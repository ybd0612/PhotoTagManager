## ⛔ 排除理由（2026-10-16，用户裁定移除）

**一句话**：它能给粗粒度概念排序，但给不了用户真正想要的细粒度标签，而为此要付出 516 MB 下载 + 一个必须人工逐条确认的交互。

### 三条实测依据

| # | 实测 | 数字 |
|---|---|---|
| 1 | **准确率不达标** | SigLIP 224² 同批样本期望类别 top-1 = **0/13**、进前三 1/13；换 SigLIP2-384 后 top-1 **3/13**、进前三 12/13。**top-1 仍不足以自动打标** |
| 2 | **细粒度属性几乎全错** | 用一张真实人像测 12 个属性标签：**排第一的是「短发」（错）、第二是「男性外表」（错）**；真实情况是长发、女性。**越细的标签越不可靠** |
| 3 | **代价与收益不匹配** | 下载 **约 516 MB**（双塔 483 MB + 分词器 33 MB），换来一个「必须逐条人工勾选、且勾对率不高」的界面 |

### 最容易被误解的一条：**它不是打标模型，是打分器**

用户当时以为「给一张图能分析出『人类、女性、长发、室内』这样的很多标签」—— **这个理解不对，而且是这类模型最弱的方向**：

- **它造不出标签**。你不在候选词表里写「长发」这个词，它永远不会想到；
- **细粒度属性在训练语料里被严重忽略**。模型见过的是图注「一个女人在室内自拍」这种粗描述，
  不是「长发、不微笑、单人」。所以粗粒度（人像/风景）它能排对，细粒度（长发/女性）它排不对。

**要「细粒度标签」需要的是另一类模型（image captioning，如 Florence-2 / BLIP-2 / Qwen2-VL）**，
那是 500 MB ~ 2 GB 量级、且多数需要自己转 ONNX —— 超出本项目当前边界。

## 0. 为什么是 SigLIP 而不是 CLIP（本文存在的理由）

用户原计划是 CLIP ViT-B/32（文档 §3A2 写的就是它）。**2026-10-07 准入查证发现 CLIP 过不了准入**，换 SigLIP 的原因有三条，按重要性排：

| # | 原因 | CLIP ViT-B/32 | **SigLIP base-patch16-224** |
|---|---|---|---|
| 1 | **一手仓 SPDX 标识** | ❌ **查不到**（`openai/clip-vit-base-patch32` 的 `cardData.license` 为 `undefined`，README 里也无任何许可声明） | ✅ **`apache-2.0`** |
| 2 | 视觉塔量化后体积 | 84.5 MB（`vision_model_q4`） | **60.3 MB** |
| 3 | 训练语料 | WebLi 英文为主 | WebLi。~~中文零样本预期更好~~ ❌ **2026-10-07 实测推翻，见 §5c：中文得分 0/13 张胜出，本项目场景下应使用英文标签** |

第 1 条是**决定性的**：按 `../design/model-licensing-and-survey.md` §3.0 白名单原文——

> 拿不到明确 SPDX 标识、或许可写不清的 → **直接按「不列」处理，不进入讨论环节**

而 §3.1 的「可用（附披露）」改判**只对「标识已在白名单内、但 LICENSE 文件本体找不到」这一格有效**，救不了「标识本身缺失」。所以 CLIP 不是「风险高一点」，而是**按现有规则直接出局**。

### 查证时一并排除的候选（避免以后重复查）

| 候选 | 结果 | 依据 |
|---|---|---|
| `Xenova/dinov2-small` | ❌ 标识缺失 | `cardData.license` 与 LICENSE 文件**均无** |
| `Xenova/mobileclip_s0` | ❌ 不在白名单 | 标识 `other`，正文是 **Apple 专有许可**（含商标限制，非开源） |
| `apple/DFN5B-CLIP-ViT-H-14` | ❌ 不在白名单 | 标识 `apple-amlr` |
| `Xenova/siglip2-base-patch16-224` | —镜像仓不存在 | 只在 `google/` 一手仓有；且比 SigLIP 1 大一代，成本更高 |
| `openai/clip-vit-base-patch32` | ❌ 见上| 一手仓也无任何许可声明 |

> **一条方法论记录**：`Xenova/*` 这一批 ONNX 转导出仓**普遍不带 SPDX 标识**（实测 clip / dinov2 / beit / resnet-50 / vitmatte 全部 `undefined`，只有 modnet 与 RMBG-1.4 例外）。所以「查镜像仓的 license 字段」这条路对多数候选会直接撞墙，**必须回到一手仓查**。

### 为什么只查了视觉塔、文本塔没动

> **⚠️ 本小节已于 2026-10-07 失效**——文本塔已于同日补测（见 §4b/§4c）。保留原文是为了说明**当初为什么先测视觉塔**，以及那个决策后来被证明是对的（视觉塔跑通后才敢断定文本塔风险同构）。
>
> 原内容：零样本打标需要**图像塔 + 文本塔**（把标签文字编码成向量再和图像向量比）。先只查视觉塔，因为——
>
> - 视觉塔是**模型的主体**（60 MB，含全部 Transformer 结构），也是**DirectML 崩溃风险所在**（K2）—— 真机探针只需要它就能回答「跑不跑得通」；
> - 文本塔是标准 Transformer + 词表查表，**算子结构与视觉塔同构**，DirectML 风险性质相同、无新增风险类型；
> - 但**它仍是未验项**，在真正做功能时必须一并实测。
>
> **不许把「视觉塔跑通」说成「SigLIP 跑通」。** 这条纪律当时成立，现在因为文本塔已补测而兑现。

**补测结果（2026-10-07）**：文本塔 DirectML / CPU **均跑通**（8ms / 29ms），且**双塔 `pooler_output` 同为 768 维、随机张量余弦相似度 -0.0036** —— 两个塔处在同一投影空间，**「能跑」之外最关键的机制验证也过了**。文本塔另有一处与同名 PyTorch 模型不同：**导出的 ONNX 只有 `input_ids`，没有 `attention_mask`**。

## 3. 能力边界

- **它不是打标模型，是「评分器」。** 产出 768 维向量，**「这张图属于哪个标签」这一步还没做** —— 需要候选词表 + 余弦相似度 + 阈值。
- ⚠️ **它不能凭空造标签。** 零样本的含义是「给一张图和**一个词**，打一个分」，不是「看图说话」。想让它自由输出标签文字，需要另一类模型（A15 BLIP-2 / Florence-2，500 MB 起且撞 K3）。**所以「自动生成标签」在实现上必然是「内置候选词表 + 模型从中挑」，这一点在 `../design/ai-photo-processing.md` §9.1 规则 2 里已写明。**
- **零样本 ≠ 什么都认得。** 它认的是 WebLI 语料里的概念。用它打「爷爷的生日」这类**具体到个人的标签**大概率失败 —— 零样本的强项是通用概念（风景/动物/美食），不是私人语义。这一点必须写进界面文案，否则用户会以为它什么都能认。
- **⚠️ 实测：不能直接用中文标签。** 见 §5c —— 官方 ONNX 导出的 tokenizer 词表**没有中文单字**（32000 条里 0 个），中文只能按 UTF-8 字节喂，模型接收到的是无意义字节。**13 张真实样本里中文得分 0 次胜出。** 结论：**候选词表必须用英文，界面层再做中文映射。**
- **⚠️ 实测：相似度是负数也不代表失败。** SigLIP 用 sigmoid loss，分数在 0 附近上下浮动、大量为负（实测区间 -0.082~ 0.069）。**任何绝对值阈值都不能想当然**，详见 §5b。
- **标签体系的决定权在用户，不在模型。** 已定规则见 `../design/ai-photo-processing.md` §9.1，核心一条：**已存在的标签只读不改**。
- 本模型**不做通用分割、不做人像抠图**，那些是 A8（u2netp / MODNet）的地盘。

### 4c. 双塔配对（**决定打标逻辑是否成立**）

| 项 | 结果 |
|---|---|
| 两个塔的输出键 | 都是 `['last_hidden_state', 'pooler_output']`，取 `pooler_output` |
| 向量维度 | 视觉 **768** ／ 文本 **768**（一致） |
| **随机张量的余弦相似度** | **-0.00362** |
| 判定 | ✅ **两个塔处在同一投影空间**。若空间不一致，这个数会显著偏离 0，打标逻辑根本不成立 —— 这是「能跑」之外必须验的那一项 |

### 三条结论

1. **DirectML 在两个塔上都跑通了，且没有静默回落 CPU。** 依据：视觉塔 27 ms vs CPU 310 ms（**11.5×**）、文本塔 8 ms vs CPU 29 ms（**3.6×**）。若 DML 实际落到 CPU，两者数字应该接近。
2. **CPU 兜底成立（K6）。** 打标是「图像一次 + 标签若干次」的配对计算，文本塔标签向量**可一次性预编码缓存**（词表是固定的），所以 CPU 路线的真实成本是「视觉塔 310 ms + 文本塔首编 29 ms」，量级完全可用。**这是 SigLIP 相对 BiRefNet 那类模型（CPU 侧 10 分钟不结束、吃 6.3 GB）的压倒性优势** —— 224² 输入 + base 规模 + 4bit 量化决定的。
3. **K7 那条 60 秒体验线毫无压力**（最大 340 ms，余量两个数量级）。所以本条目**不因慢而出局**，可以考虑进清单。

### ⚠️ 口径警告（三条，都要带着引用）

1. **「未静默回落 CPU」是推断，不是直接证据。** 靠耗时差反推。要彻底钉死仍依赖 `../design/gpu-self-probe.md` 第 0 步 P1「DirectML 到底选哪块卡从未验证」那个未结问题。
2. **`heapΔ` 是 Node 堆增量，不是显存。** K3 那条 `minVramMiB` 标定仍未做。
3. **随机张量的相似度只验机制，不验准确率。** `-0.00362` 说明「空间一致、机制可用」，但**真实照片配真实标签时的相似度分布完全没有测**（见 §5）。

## 5. 真图验收

**已做 13 张真实样本的零样本实测**（2026-10-07）。结论有两条，其中一条**推翻了本卷宗§0 的第3 条推断**。

样本取自用户真实图片库（不是网上找的图）：`C:\Users\ybd06\Pictures\PixPinAutoSave` 均匀抽 12 张截图 + `Pictures\test` 唯一那张人像。**这个分布本身也是一条结论**——见 §5c 末条。

### 5a. 候选词表命中率（16 个候选 = 8 中文 + 8 英文，中英同义）

> ❌ **本小节的数字已被 2026-10-16 的复测推翻，不要再引用「8/13」。**
> 原因见 §5d 未验项 8：当时用的是自写 tokenizer，**没有把英文单词间的空格转成 `Metaspace` 的 `▁`**，
> 喂给文本塔的 `input_ids` 本身就是错的。复测见 §5e。原文保留如下，只为可追溯。

| 指标 | 结果 |
|---|---|
| 期望标签排**第 1** | **8/ 13**（⚠️ 不可信，见上） |
| 期望标签进**前三** | **10 / 13**（⚠️ 不可信，见上） |
| 期望标签排第 5 及以后 | 3张（1 张截图、1 张人像） |
| 单图耗时 | 首图 341ms（含首次预热），其余 **38–73ms** |

### 5b. 相似度分布 —— 绝对值低得超出预期

| 项 | 范围 |
|---|---|
| 全部 16 个候选的相似度 | **-0.0821 ~ 0.0692** |
| 中文标签最高分 | -0.0028 ~ +0.0315 |
| 英文标签最高分 | -0.0319 ~ +0.0692 |

⚠️ **这组数字否掉了一个想当然的做法**：SigLIP 用sigmoid loss，**它的余弦相似度不会像 CLIP 那样集中在 0.2~0.3**，而是**在 0 附近上下浮动、大量为负**。所以：

- **照搬 CLIP 的「相似度 > 0.25 就算匹配」这套阈值会全军覆没**——没有任何一张图的分数能到 0.25。
- 阈值必须**实测标定**，且**不能是绝对值**，更可能要做**「top-1 与 top-2 的差值」这类相对判据**（本轮实测里，命中第一名的样本其 top1 一般领先 top2 约 0.002~0.014，量级很小）。

### 5c. ❌ 中文能力：**实测推翻了我此前的推断**

§0 第 3 条我写过「SigLIP 训练语料含中文，中文零样本预期更好」。**实测结果是相反的：**

| 项 | 结果 |
|---|---|
| **中文标签得分更高的样本** | **0 / 13** |
| top-3 里出现中文标签的样本 | 仅 1 张（人像那张，且排第 2，**分数还低于同义的英文**） |

**原因已定位到词表层面**：`tokenizer.json` 的 32000 条词表里，**中文单字 0 个**，只有 256 条 `<0xXX>` 字节级条目 + 31744 条英文词/字符。中文只能按 UTF-8 字节切成一个 16 字节的序列去喂，模型接收到的是「一串无意义字节」而非词义。**这不是模型能力问题，是这个 ONNX 导出版本没带中文词表。**

> **一条实测教训**：分词器第一版我用「标签长度凑 token id」的近似写法，测出「中文全是unk」却没先核对词表，一度准备把结论写成「SigLIP 中文能力差」。真正的原因是**词表根本没有中文单字**——两者结论相似，但归因完全不同，后者会误导后续「换个中文模型就行」的判断。**归因错了，结论对了也没用。**

**所以本项目要用英文标签做候选词表**，界面上再映射成中文显示（映射是纯查表，零模型成本）。这一条已写进 §7 待办 3。

### 5d. 未验项（不许当成已验）

1. **候选词表只有 16 个词，是最小验证集**。命中率 8/13 这个数字**不能外推**到几百个候选词的真实词表——词表越大，误命中越多。**真实词表的命中率必须重测。**（且 8/13 本身已被 §5e 推翻）
2. **人像那张排第 7 名**（期望「人像照片」，实际 top1 是「a software interface」）。**这一条值得警惕**：它是唯一一张非截图、且是真人肖像的图。若真实相册里人像较多，候选词表必须覆盖「人像」这一类，且要重测。
3. **本轮预处理是「短边缩到 224 + 中心裁剪」**，截图因此被裁掉大量边缘信息。这与生产管线一致，但**截图类内容靠边缘文字区分**，「文档截图」排第 3 而非第 1 可能与此有关。是否该为截图类改用「整图压进224²」（不裁剪）**未测**。
4. **DirectML 究竟跑在哪块卡未验** —— 4 个虚拟显示器（向日葵 / ToDesk / GameViewer）本机已实测枚举到，`2026-10-07` 已修 `classifyAdapters`，但**「判定逻辑修对了」不等于「DML 选卡正确」**，仍阻塞在 `gpu-self-probe.md` 第 0 步 P1。
5. **装机版端到端未跑** —— 只在纯 node 进程跑过，未经 Electron 推理子进程与真实 UI 链路（`verify:ai-child` 那条路）。
6. **真实显存/内存峰值未测** —— §4 的 `heapΔ` 是 Node 堆增量，**不是显存**。K3 那条 `minVramMiB` 标定仍未做。
7. **文本塔双源比对未做** —— 视觉塔两源逐字节一致，文本塔只在 hf-mirror 验了哈希。
8. ~~分词器是自实现的贪心最长匹配~~ → **已解决（2026-10-16）**：生产改用官方 `@huggingface/tokenizers` 0.1.3，
   读本机下载的 `tokenizer.json`（SHA-256 `4a17c975…`，双源逐字节一致）。**官方实现完整支持
   `Precompiled` normalizer、`Replace(/ {2,}/)`、`Metaspace`、Unigram Viterbi 与 `</s>` 模板**，
   词间空格正确转成 `▁`（实测 `a portrait photo` → `["▁","a","▁portrait","▁photo","</s>"]`）。
   ⚠️ **仍未做**：与 Rust `tokenizers` 的逐 id 对照（本机装不上 Rust 版），所以"官方实现"是可信来源但非等价性证明。
   ⚠️ **§5a 的 8/13 就是在分词错误下测出来的**，因此该数字不能作为功能准入依据，见 §5e。

### 5e. 2026-10-16 复测：换官方 tokenizer 后，正确率**不升反降**

这一节推翻 §5a，并直接决定了「它进不了清单」。

**测法**：换官方 `@huggingface/tokenizers` 0.1.3 读同一份 `tokenizer.json`；
图像侧改用**生产预处理**（`preprocessImage`：短边缩到 224 + 居中补边 + `[-1,1]` 归一化，
与 `portrait-cutout` 同一套代码路径）；样本仍是原来那 13 张真实照片（12 张截图 + 1 张人像）。

**结果（8 个英文候选，单 prompt）**：

| 指标 | 结果 |
|---|---|
| 期望类别 top-1 | **0 / 13** |
| 期望类别进前三 | **1 / 13**（那张人像，排第 3） |
| 截图样本里期望类别名次 | 第 4 ~ 第 8 名，无一进入前三 |
| 相似度区间 | 约 -0.06 ~ +0.04（**确认了 §5b：绝对值阈值不成立**） |

**换 prompt 模板也没有救回来**。同一批样本上试了 6 种模板（裸词 / `a X` / `a photo of a X` /
`a picture of a X` / `This is a X.` / `a photo showing X`），以及"每个概念多条 prompt 取 max"
的集成口径：

| 口径 | top-1 | 进前三 | 平均名次 |
|---|---|---|---|
| 多 prompt 取 **mean** | 0 / 13 | 1 / 13 | 4.69 |
| 多 prompt 取 **max** | 2 / 13 | 6 / 13 | **3.92** |
| 多 prompt 取 top3 均值 | 1 / 13 | 5 / 13 | 4.08 |

**结论（这三条是产品决策的依据，不是待办）**：

1. **§5a 的「8/13 top1」是错的，不能引用。** 它诞生于一个把英文词间空格漏掉的 tokenizer；
   换成官方实现后同一批样本的命中不升反降。**归因不同比数字错更要紧**：不是"SigLIP 不行"，
   而是"当时量的是噪声"。
2. **当前这套 8 词候选表不足以支撑自动打标。** 截图类尤其差——这类内容靠边缘文字区分，
   而 224² 输入把它压成了几块色块。
3. **所以产品口径定为「只建议、人来判」**：不给任何置信度阈值，不预勾选，
   分数原样透传并明说"不代表准确率"。取 max 的集成口径在集成测试里落地
   （见 `tests/ai/siglip.test.ts`），因为它是实测里唯一明显更好的一档。

**仍未验**：真实相册规模（几十个概念）上的命中率；截图专用预处理（整图压进 224²，不裁剪）；
与 Rust `tokenizers` 的逐 id 等价性。**这三项没做之前，本条目不进能力清单。**

### 5h. ⚠️ 同一张图暴露的真问题：**竖图的有效分辨率受限于宽度**

那张人像是 **1080 × 1440（3:4 竖图）**。等比缩到 224² 时：

```
缩放系数 0.4630  →  内容区 224 × 299  （上下补边各 62 px）
★ 宽度只剩 224 px（原图 1080 px）：每 5 个原图像素挤成 1 个
```

**竖图的缩放由高度决定**，所以 1080 宽的照片进 224 见方窗口，宽度只剩 224。
人脸在画面里占比不大，**模型看到的是一张 224 宽的糊图** —— 这就是分数停在
**-0.0001**（与 0 几乎同值、第二名只差 0.004）的直接原因。

**不是模型不会认人像，是它拿到的那张糊图里，「人」和「软件界面」确实难分。**

⚠️ **这条修正了我此前「分辨率是主要瓶颈」的笼统说法**，要分图型看（§5g 的 384 版实测印证）：

| 图型 | 受限于 | 384² 是否够 |
|---|---|---|
| **截图类（宽幅，如 4608×3072）** | 面积 | ✅ 够 —— 进前三 1/13 → **12/13** |
| **人像竖图（如 1080×1440）** | **宽度** | ❌ **仍不够**（见 `tagging-candidates.md` §2.1） |

**这类图的解法是「切块」（把脸放大再送），不是换更大分辨率的模型** ——
再换 768² 也只是把同一张糊图放大一点。

## 6. 与已有能力的关系

- 复用现有标签链路：产物是**标签**，走既有的 `XMP-ptm:Tags` 写入路径，**不新增产物形态**。
- **它是A17 相似检索的地基**（文档 §3A17「唯一正确技术路线」）。若这条走通，A17 / E3 连拍精选 / E4 找重复 / D1 NSFW / G5 地标 / K2 属性 / K3 事件类型 **全部受益**——这是「一次投入、多处受益」价值最高的一项。
- 与 A1 图像分类**不是替代关系**：A1 是封闭标签集的分类器（快、小、无需文本塔），A2/SigLIP 是开放词表的编码器。**封闭场景先走 A1**。
