## 0. 为什么是 SigLIP 而不是 CLIP（本文存在的理由）

用户原计划是 CLIP ViT-B/32（文档 §3A2 写的就是它）。**2026-10-07 准入查证发现 CLIP 过不了准入**，换 SigLIP 的原因有三条，按重要性排：

| # | 原因 | CLIP ViT-B/32 | **SigLIP base-patch16-224** |
|---|---|---|---|
| 1 | **一手仓 SPDX 标识** | ❌ **查不到**（`openai/clip-vit-base-patch32` 的 `cardData.license` 为 `undefined`，README 里也无任何许可声明） | ✅ **`apache-2.0`** |
| 2 | 视觉塔量化后体积 | 84.5 MB（`vision_model_q4`） | **60.3 MB** |
| 3 | 训练语料 | WebLi英文为主 | WebLi，**中文零样本表现预期更好**（⚠️ 未实测，见 §5 未验项） |

第 1 条是**决定性的**：按 `../design/model-licensing-and-survey.md` §3.0 白名单原文——

> 拿不到明确 SPDX 标识、或许可写不清的 → **直接按「不列」处理，不进入讨论环节**

而 §3.1 的「可用（附披露）」改判**只对「标识已在白名单内、但 LICENSE 文件本体找不到」这一格有效**，救不了「标识本身缺失」。所以 CLIP 不是「风险高一点」，而是**按现有规则直接出局**。

### 查证时一并排除的候选（避免以后重复查）

| 候选 | 结果 | 依据 |
|---|---|---|
| `Xenova/dinov2-small` | ❌ 标识缺失 | `cardData.license` 与 LICENSE 文件**均无** |
| `Xenova/mobileclip_s0` | ❌ 不在白名单 | 标识 `other`，正文是 **Apple 专有许可**（含商标限制，非开源） |
| `apple/DFN5B-CLIP-ViT-H-14` | ❌ 不在白名单 | 标识 `apple-amlr` |
| `Xenova/siglip2-base-patch16-224` | —镜像仓不存在 | 只在 `google/` 一手仓有；且比 SigLIP 1 大一代，成本更高 |
| `openai/clip-vit-base-patch32` | ❌ 见上| 一手仓也无任何许可声明 |

> **一条方法论记录**：`Xenova/*` 这一批 ONNX 转导出仓**普遍不带 SPDX 标识**（实测 clip / dinov2 / beit / resnet-50 / vitmatte 全部 `undefined`，只有 modnet 与 RMBG-1.4 例外）。所以「查镜像仓的 license 字段」这条路对多数候选会直接撞墙，**必须回到一手仓查**。

### 为什么只查了视觉塔、文本塔没动

> **⚠️ 本小节已于 2026-10-07 失效**——文本塔已于同日补测（见 §4b/§4c）。保留原文是为了说明**当初为什么先测视觉塔**，以及那个决策后来被证明是对的（视觉塔跑通后才敢断定文本塔风险同构）。
>
> 原内容：零样本打标需要**图像塔 + 文本塔**（把标签文字编码成向量再和图像向量比）。先只查视觉塔，因为——
>
> - 视觉塔是**模型的主体**（60 MB，含全部 Transformer 结构），也是**DirectML 崩溃风险所在**（K2）—— 真机探针只需要它就能回答「跑不跑得通」；
> - 文本塔是标准 Transformer + 词表查表，**算子结构与视觉塔同构**，DirectML 风险性质相同、无新增风险类型；
> - 但**它仍是未验项**，在真正做功能时必须一并实测。
>
> **不许把「视觉塔跑通」说成「SigLIP 跑通」。** 这条纪律当时成立，现在因为文本塔已补测而兑现。

**补测结果（2026-10-07）**：文本塔 DirectML / CPU **均跑通**（8ms / 29ms），且**双塔 `pooler_output` 同为 768 维、随机张量余弦相似度 -0.0036** —— 两个塔处在同一投影空间，**「能跑」之外最关键的机制验证也过了**。文本塔另有一处与同名 PyTorch 模型不同：**导出的 ONNX 只有 `input_ids`，没有 `attention_mask`**。

## 3. 能力边界

- **它不是打标模型，是「评分器」。** 产出 768 维向量，**「这张图属于哪个标签」这一步还没做** —— 需要候选词表 + 余弦相似度 + 阈值。
- ⚠️ **它不能凭空造标签。** 零样本的含义是「给一张图和**一个词**，打一个分」，不是「看图说话」。想让它自由输出标签文字，需要另一类模型（A15 BLIP-2 / Florence-2，500 MB 起且撞 K3）。**所以「自动生成标签」在实现上必然是「内置候选词表 + 模型从中挑」，这一点在 `../design/ai-photo-processing.md` §9.1 规则 2 里已写明。**
- **零样本 ≠ 什么都认得。** 它认的是 WebLI 语料里的概念。用它打「爷爷的生日」这类**具体到个人的标签**大概率失败 —— 零样本的强项是通用概念（风景/动物/美食），不是私人语义。这一点必须写进界面文案，否则用户会以为它什么都能认。
- **标签体系的决定权在用户，不在模型。** 已定规则见 `../design/ai-photo-processing.md` §9.1，核心一条：**已存在的标签只读不改**。
- 本模型**不做通用分割、不做人像抠图**，那些是 A8（u2netp / MODNet）的地盘。

## 4. 实测数字（开发机 RTX 5060 Laptop + AMD 610M，**不得当产品承诺**）

探针脚本 `C:\Users\ybd06\temp\siglip-probe\probe.cjs` 与 `probe-text.cjs`（临时产物，未进仓库）。随机张量，**6 次取第 2–6 次的中位数**；CPU侧按 D12 限 `intraOpNumThreads=2`。

### 4a. 视觉塔（输入 `[1,3,224,224]`）

|------|------|------|------------------------|-------|
| 2026-10-07 | **DirectML** | **645 ms** | 369 ms / **27 ms** / 26 ms / 28 ms | +0.6 MB |
| 2026-10-07 | **CPU（2 线程）** | 243 ms | 308 ms / **310 ms** / 272 ms / 340 ms | +0.2 MB |

### 4b. 文本塔（输入 `[1,16]`，序列长 16）

| 日期 | 后端 | 加载 | 推理（首次 / 中位 / 最小 / 最大） | 输出值域 |

| 2026-10-07 | **CPU（2 线程）** | 202 ms | 31 ms / **29 ms** / 29 ms / 30 ms | 同上（两后端逐位相同） |

### 4c. 双塔配对（**决定打标逻辑是否成立**）

| 项 | 结果 |
|---|---|
| 两个塔的输出键 | 都是 `['last_hidden_state', 'pooler_output']`，取 `pooler_output` |
| 向量维度 | 视觉 **768** ／ 文本 **768**（一致） |
| **随机张量的余弦相似度** | **-0.00362** |
| 判定 | ✅ **两个塔处在同一投影空间**。若空间不一致，这个数会显著偏离 0，打标逻辑根本不成立 —— 这是「能跑」之外必须验的那一项 |

**输出形态核对**：两塔的 `last_hidden_state` 值域一致（`[-6.157, 9.223]`），finite、无 NaN，**量化后没有数值崩坏**。

### 三条结论

1. **DirectML 在两个塔上都跑通了，且没有静默回落 CPU。** 依据：视觉塔 27 ms vs CPU 310 ms（**11.5×**）、文本塔 8 ms vs CPU 29 ms（**3.6×**）。若 DML 实际落到 CPU，两者数字应该接近。
2. **CPU 兜底成立（K6）。** 打标是「图像一次 + 标签若干次」的配对计算，文本塔标签向量**可一次性预编码缓存**（词表是固定的），所以 CPU 路线的真实成本是「视觉塔 310 ms + 文本塔首编 29 ms」，量级完全可用。**这是 SigLIP 相对 BiRefNet 那类模型（CPU 侧 10 分钟不结束、吃 6.3 GB）的压倒性优势** —— 224² 输入 + base 规模 + 4bit 量化决定的。
3. **K7 那条 60 秒体验线毫无压力**（最大 340 ms，余量两个数量级）。所以本条目**不因慢而出局**，可以考虑进清单。

### ⚠️ 口径警告（三条，都要带着引用）

1. **「未静默回落 CPU」是推断，不是直接证据。** 靠耗时差反推。要彻底钉死仍依赖 `../design/gpu-self-probe.md` 第 0 步 P1「DirectML 到底选哪块卡从未验证」那个未结问题。
2. **`heapΔ` 是 Node 堆增量，不是显存。** K3 那条 `minVramMiB` 标定仍未做。
3. **随机张量的相似度只验机制，不验准确率。** `-0.00362` 说明「空间一致、机制可用」，但**真实照片配真实标签时的相似度分布完全没有测**（见 §5）。

## 5. 真图验收

**未做。** 本条目完成了「双塔能跑 + 投影空间一致」，**没有验证「打标准不准」**。

- **未验项（不许当成已验）**：
  1. **真实照片上的零样本准确率未测** —— 需要一份候选词表 + 真图对。这是**当前最大的未知**，也是「置信度阈值」定不出来的根因。
  2. **中文标签未验** —— §0 第 3 条说 SigLIP 中文预期更好，**这是我从训练语料推断的，没有实测支撑**。真要用中文词表，**必须先实测**：拿 20~30 个中文标签跑一批自己的照片，看分数分布能不能分开。
  3. **tokenizer 未接** —— 文本塔输入是 `input_ids`，需配套 tokenizer（`tokenizer.json` + `spiece.model`，**注意导出的 ONNX 没有 `attention_mask` 输入**）。这属实现期工作，未验。
  4. **相似度分布未测** —— §4c 那个 `-0.00362` 是**随机张量**的基线，只证明空间一致。真实图像与真实标签的相似度落在什么区间、阈值该切在哪，**完全没有数据**。
  5. **DirectML 究竟跑在哪块卡未验** —— 4个虚拟显示器（向日葵 / ToDesk / GameViewer）本机已实测枚举到，`2026-10-07` 已修 `classifyAdapters`，但**「判定逻辑修对了」不等于「DML 选卡正确」**，仍阻塞在 `gpu-self-probe.md` 第 0 步 P1。
  6. **装机版端到端未跑** —— 只在纯 node 进程跑过，未经 Electron 推理子进程与真实 UI 链路（`verify:ai-child` 那条路）。
  7. **真实显存/内存峰值未测** —— §4 的 `heapΔ` 是 Node 堆增量，**不是显存**。K3 那条 `minVramMiB` 标定仍未做。
  8. **文本塔双源比对未做** —— 视觉塔两源逐字节一致，文本塔只在 hf-mirror 验了哈希。

## 6. 与已有能力的关系

- 复用现有标签链路：产物是**标签**，走既有的 `XMP-ptm:Tags` 写入路径，**不新增产物形态**。
- **它是A17 相似检索的地基**（文档 §3A17「唯一正确技术路线」）。若这条走通，A17 / E3 连拍精选 / E4 找重复 / D1 NSFW / G5 地标 / K2 属性 / K3 事件类型 **全部受益**——这是「一次投入、多处受益」价值最高的一项。
- 与 A1 图像分类**不是替代关系**：A1 是封闭标签集的分类器（快、小、无需文本塔），A2/SigLIP 是开放词表的编码器。**封闭场景先走 A1**。
