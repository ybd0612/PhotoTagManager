# 图像模型能力地图（Image Model Capability Map）

> 建档 2026-09-29。来源：一次「图片处理领域一共有哪几类模型」的调研 + 本项目已定案的引擎与硬件约束。
> **这是地图，不是承诺清单。** 全文没有任何一条模型通过本机推理验证（除 §10 明确列出来源的那几条）。

## 0. 先读这条硬规则

`docs/design/ai-photo-processing.md` §4.3 定过一条不可绕过的规则：**只有「已跑通」的条目才能出现在用户界面里**。本文件不削弱它，也不提供绕过它的路径。

因此本地图里每一行的正确用法是：

- 想清楚"这个能力值不值得做" → 看本文件；
- 想把它变成产品功能 → 必须再走 §8 的四步流程，最后进 §4.3 那张表；
- **直接把本文件的某一行抄进 `electron/ai/capabilityCatalog.ts` 或界面文案 = 违规。**

历史教训有两条，都是本项目的真钱换来的：

1. 镜像上名为 `Real-ESRGAN-ONNX` 的仓库，`model.onnx` 实际是 **0.0 MB 的 Git LFS 指针**。"文件存在"不等于"文件能下"。
2. 同一引擎上 u2netp 跑得漂亮、BiRefNet 一执行就抛 `DmlFusedNode` 原生错误。"文件能下"不等于"功能可用"。

## 1. 判据：本项目独有的 8 条硬约束

一个模型类别在别处再有用，撞进这 8 条就不适合本项目。来源分三类，**引用时要看准是哪一类**：

- **K1–K5** 来自已定案内容（D11/D12、AG1、M0 实测），是实测与裁定过的硬事实。
- **K6、K8** 是 2026-09-29 用户新增的方向，其中 K6 不排除能力、只给同能力实现排序。
- **K7 的数值（1 分钟）是用户当日口头拍的临时值，不是实测校准的结果**，将来要按真机数据收紧或放宽。

| # | 约束 | 对选型的直接影响 |
|---|------|-----------------|
| **K1** | **纯本地推理，不做云端 API 兜底** | 排除所有只能云端用的闭源能力（Adobe Sensei 类自动增强、Midjourney 类）。 |
| **K2** | **引擎 = `onnxruntime-node` + DirectML**（CUDA 在 npm 预编译包里不存在；ort-web 的 WebGPU 在 Electron 31 会话创建死锁） | 必须是**能导出 ONNX、且算子被 DirectML 支持**的模型。Transformer 里花哨算子（自定义 attention kernel、动态 shape）是崩溃高发区。 |
| **K3** | **显存是用户侧变量，不是常量**。开发机 = RTX 5060 Laptop **8151 MiB**（整卡共享），但发布后要面对 4 GB 独显、核显、以及远程桌面虚拟适配器 | 单次前向的小中型模型在开发机上安全，但"这台机器跑不跑得动"**必须按用户机器判定，见 §1.5**；多步采样的扩散模型 + 文本编码器 + VAE 同驻，在任何目标机上基本都越线。 |
| **K4** | **安装包已 121 MB，模型按需下载** | 模型体积直接决定用户是否愿意点下载。**>300 MB 的条目要单独论证**。 |
| **K5** | **零出站（AG1）** | 只能本地算。任何要联网查库/调云端精修的能力出局。 |
| **K6** | **双后端可跑**（2026-09-29 新增，用户定的方向） | 见下方专节：**它不用于排除能力，用于在同能力的多个实现之间排序**。 |
| **K7** | **响应耗时上限：单次操作超过 1 分钟即算"慢到不可用"**（2026-09-29 用户口头裁定的**临时值，未经实测校准**） | 此前本表只要求"去记录耗时"，**没有一条给出合格线**——那等于任何慢模型都能过。现在这条才是挡它的：GPU 路径下推理超 60 秒，或批量单张折算超线 → 判 ✗ 或降为 ○。**待校准项**：批量（M4）场景的单张折算上限应比单点操作更宽，还没定。 |
| **K8** | **内存与 CPU 核数同样是用户侧变量**（开发机 **32 GB 内存 / 32 逻辑核**，发布后要面对 8 GB、16 GB 机器） | 此前只把"CPU 跑 BiRefNet 吃 **6.3 GB**"当成 CPU 不可用的附证，**没把 RAM 本身当约束**——这是 K3 那个"拿开发机数字当产品常量"的病在同一处的第二次发作。所以选型除显存外还须记**内存增量**；而"限几线程"这条也不能按 32 核定，要给绝对上限（本轮实测：2→4 线程只快 28%，加核数收益很快见顶）。 |

### K6 详解：CPU 兜底是准入偏好，不是魔法

**动机**：本项目是消费级装机软件，用户机器参差不齐，而 CPU 兜底是唯一不依赖显卡品牌的退路。

**技术上它几乎免费**：ONNX 文件是**同一份权重**，DirectML 后端与 CPU 后端读同一个 `.onnx`，不需要为 CPU 另找模型、不多下载任何东西。代码里这条路已经通了——`electron/ai/inferenceChild.ts:20` 有 `BackendPreference = 'dml' | 'cpu'`，`:38` 写的是 `executionProviders: backend === 'dml' ? ['dml', 'cpu'] : ['cpu']`，`src/components/AiActionSplitButton.tsx` 里已有「CPU 慢速模式」勾选。

**但"只是 CPU 慢一点"这个预期已被实测否证，必须按绝对耗时看**：

| 模型 | 体积 | GPU | CPU | 倍率 | CPU 实际可用性 |
|------|------|-----|-----|------|--------------|
| u2netp | 4.4 MB | 21 ms | 201 ms（限 2 线程） | 约 10× | ✅ 0.2 秒，完全可用 |
| BiRefNet-lite | 214 MB | 执行即崩 | **10 分钟不结束** | — | ❌ 吃 **6.3 GB** 内存、把整机压到死机 |

**倍率不是判据，绝对耗时和内存占用才是。** 慢 10 倍的 21 ms 是惊喜，慢 10 倍的 5 秒已经开始考验耐心。

**由此定下的三条做法**：

1. **选型偏好**：同一项能力有两个以上候选实现时，**"CPU 也跑得动"的那个优先级更高**，哪怕它在 GPU 上稍慢一些。
2. **准入要求**：进清单的每条模型必须交**两组实测数字**（GPU 一次、CPU 一次），CPU 那组记限线程后的绝对耗时与内存增量（见 §8 第 3 步）。
3. **允许显式例外，但**不置灰挡死：CPU 实测越过阈值的条目，在清单里标 **「仅 GPU（本机 CPU 约需 N 分钟）」**，**按钮仍然可点**，但点之前就给出预计耗时、执行中保留「取消」。
   - 依据：本项目既有取向就是不置灰——`src/components/AiActionSplitButton.tsx:309` 那个「· 不可用」**只是文案，没有 `disabled`**，同文件 `:140` 的注释还写着"进行中不置灰：用 disabled 表达忙会让人以为程序坏了"。
   - 这一条同时消掉本文早先的一处跨节矛盾：K6 原写"把 CPU 勾选置灰"，而 §1.5 写"绝不置灰挡死"。**统一按不置灰执行。**
   - 仍然要避免的真实风险不是"可点"，而是"可点且用户不知道要等多久、也停不下来"——所以配套要求是：**预计耗时来自实测数字（K7/K8），并且有可用的取消**。

**阈值待定，不许凭空写数字**：出局线画在 50 MB 还是 150 MB，需要 Depth Anything（26 MB）、SAM（101 MB）等真跑一遍 CPU 路径才有依据。本文件**不预设阈值**；建议量级 >60 秒或内存 >4 GB 作为待验证的候选线，未经实测不得进产品文案。

### 这八条不是同一堵墙（读表时最容易犯的错）

K1–K8 并排列在一张表里，容易被读成"约束越多能用的模型就越少"，实际不是：

- **真正被 K2（引擎）单独挡掉的项非常少**——按行统计全文 **20 个 ✗ 里有 12 个来自 C 类整节**（其余：A 3、D 1、新增族 4），而 C 类的主因是产品形态（要点一下就静默出结果）与显存/体积，不是引擎无能。
- 多数条目是**多因叠加**（体积同时撞 K3 和 K4），本文件**不做逐行精确归因**，因为把多因硬拆成单一主因会造出一个看起来精确实则无据的数字。

- **K7 与 K8 跟引擎无关，别跟 K2 混成一堵墙**：K7 是**体验上限**（慢到不可用就该出局，不管它技术上多稳），K8 是**用户机器的内存与核数**。尤其 K7，它是本表里唯一一条**不由技术能力决定、纯由产品体验决定**的判据——也正是因为它此前不存在，"任何慢模型都能通过全部判据"这个洞才一直开着。

**结论**：看这张表要按"哪条墙挡哪件事"分开读，不要得出"引擎限制 = 整个方案限制"的判断。

### 1.5 用户机器不是这台开发机（2026-09-29 新增）

上面 K3/K6 的所有数字都来自开发机。这是**发布给别人的装机软件**，所以"能不能跑"在运行时才知道，而不是在清单里写死。

#### 实测：Windows 的显存查询字段会谎报一半

同一天在本机两种查法对照（命令见 §10）：

| 查法 | RTX 5060 Laptop | AMD Radeon 610M（核显） |
|------|----------------|----------------------|
| WMI `Win32_VideoController.AdapterRAM` | **4095 MiB**（值 4293918720，uint32 封顶） | 512 MiB |
| `nvidia-smi --query-gpu=memory.total` | **8151 MiB** ✅ | 读不到（非 N 卡） |

**直接后果**：如果按显存做准入判断而照搬 CIM 那个字段，一堆 8 GB 卡会被当成 4 GB，`BiRefNet`（214 MB）这类条目就会**误标不可用**——正是"探测本身谎报，然后把能用的机器挡在门外"那种冤案。这条现在没伤人，因为 `electron/ai/gpuCapability.ts:91` 只把显存读数当"有没有卡"的布尔用，**数值读完就丢**。

#### 模型要多少显存，没法从体积推

u2netp 权重只有 **4.4 MB**，一次推理整卡显存 **+325 MiB**。真正决定显存的是**输入分辨率**（BiRefNet 跑 1024²，u2netp 跑 320²），不是权重大小。**所以 `minVramMiB` 只能实测标定，没有公式可算。**

#### 三档做法（L3 已由用户认可为方向）

```
L1  每条模型声明 minVramMiB            ← 实测得出，不是体积推算
L2  探测到总显存不足 → 标「本机显存可能不足」，但【仍然可点】
      ← 绝不置灰挡死：探测自己就会谎报（见上）
L3  真跑一次 DirectML 推理当能力探测
      ← 测运行时行为，不是猜；但模型不随包发，具体形态见下方 L3a / L3b
```

**L3 为什么可靠**：任何静态查询（WMI / nvidia-smi / 适配器名）都是在猜，而跑一次真推理测的是运行时行为，顺带还能给 K6 的 CPU 对比提供同机基准。

> **2026-09-29 核实修正——本条原来的前提不成立**：原写"用**随包**的 u2netp 跑一次"，但 `package.json` 的 `build` 段**没有 `extraResources`**，模型目录也不在 `files` 里 —— **u2netp 是首次使用时才下载的 4.4 MB，不随安装包发**。于是"首次启动自动跑 L3"等于**应用自己发起一次下载**，会撞 §8-27 那条「处理期间无任何出站请求」的系统级抓包验收，也不能在用户没点过下载之前就偷偷做。
>
> **L3 的两个正确形态（待裁定，本文件不替用户选）**：
> - **L3a 被动探测（零额外动作、零出站）**：用户第一次点「抠图」本身就是一次真实推理——把它的成功/失败、耗时、整卡显存增量记进 `userData` 里的能力档案，供后续条目预判。失败分类已有雏形（`gpuErrorText` 的 `GPU_MEMORY_LOW` / `GPU_DEVICE_UNAVAILABLE`），**缺的是"认出来之后落档、并反过来影响清单标注"这一步**。
> - **L3b 合成微型 ONNX（零下载、零出站）**：程序内嵌几 KB 的固定字节数组（例如两层 Conv），首次启动在 `dml` 与 `cpu` 上各 `run` 一次。它不依赖模型下载因此不碰网络，能同时回答"DML 到底可用吗"和"这台机器 CPU 相对 GPU 慢多少倍"。**比原 L3 更优**，且顺带把 K6 缺的阈值数据一起测出来。

**一条不能破的已定裁定**：D12「**绝不自动退回 CPU**」。所以 L2/L3 探测出显存不足时，只能**标注 + 让用户自己勾 CPU**，不允许自动切、也不允许把条目置灰挡死。（另注：`inferenceChild.ts:38` 的 `['dml','cpu']` 存在引擎内部的**自动回落**，与 D12 精神冲突且当前无日志可证，已登记但未处理。）

#### 本轮发现、**未修**的漏判

`classifyAdapters`（`gpuCapability.ts:25`）只过滤掉 "Microsoft Basic" 这类占位适配器。本机实测枚举到 **3 个远程控制虚拟适配器**——`OrayIddDriver Device`（向日葵）、`Todesk Virtual Display Adapter`、`GameViewer Virtual Display Adapter`，它们 `AdapterRAM` 全为空，但**名字都不含 Basic，所以全部通过过滤被算成真实适配器**。

后果：一台只有核显 + 装了 ToDesk/向日葵的用户机器会被判 `ok`，清单全亮，点下去才报显存不足。

**本文件只登记这一条，代码未动**（用户裁定本轮只做文档）。要修的话，正确做法不是把厂商名再加长，而是**改用 L3 的运行时探测**——静态名单永远追不上国产远控驱动。

### 一条容易被忽略的派生约束：加载预算

实测过：`DEFAULT_LOAD_TIMEOUT_MS = 30_000` **装不下 224 MB 级的模型**（BiRefNet 加载 9053 ms，CPU 侧光读元数据就要 17.1 s）。

所以本地图凡是标 **>100 MB** 的行，都附带一个前置动作：**把加载超时应改成按体积计算**，否则用户会看到一条"加载超时"而不是真实失败原因。这件事在 M3 加第一个大模型之前必须做完，与选哪个模型无关。

## 2. 分类的尺子

不按"模型结构"分，按**它对像素做了什么**分——这条尺子和本项目的产品形态直接对齐（派生新文件 vs 只写标签）：

> **⚠ 尺子自身的缺陷（2026-09-29 复盘）**：「对像素做了什么」这句**默认了"单张图进、单张图出或输出信息"**，因此**结构性地漏掉三个方向**，不是少写几项那么轻：
>
> ```
> ① 多张图 → 一张图    尺子里根本没有"多输入"这个维度（HDR、多帧降噪、焦点堆栈）
> ② 图 → 几何/位置关系  输出既不是像素也不是标签，而是空间关系（匹配、配准、地理定位）
> ③ 图 → 内在成分       改光照、去反光、去阴影——卡在"不改内容"与"生成"之间，两格都不算
> ```
>
> **根因**：我先定了尺子再往里填格子，而不是先把任务族穷举完再选尺子。**以后做这类全景调研，顺序必须反过来**——先穷举、再归类，否则"看起来很完整"的分类会在自己没想到的方向上成片缺失。漏掉的族见 §7.5。

| 大类 | 本质 | 是否改像素 | 内容是否变 | 产物 | 对应本项目 |
|------|------|-----------|-----------|------|-----------|
| **A 理解/分析** | 只读图，输出信息 | 否 | — | 标签/框/掩码/数值 | 写 XMP 标签，不产文件（智能打标那条例外路径） |
| **B 恢复/增强** | 改像素，内容不变 | 是 | 否 | 派生新文件 | `原名.xxx.jpg` |
| **C 生成/编辑** | 改像素，内容会变 | 是 | **是** | 派生新文件 | 本地图判定：**本地不做**（§5） |
| **D 安全与真实性** | 判图的来路与风险 | 否 | — | 标签/标记 | 写标签 |
| **E 摄影工作流** | 组合 A/B 的能力做"挑图" | 视组合而定 | — | 排序/分组/建议 | **PRD 之外的候选方向**（§7） |
| **F 计算摄影（多图合成）** | **多张输入合成一张** | 是 | 否 | 派生新文件 | 🆕 此前整族遗漏（§7.5） |
| **G 几何与定位** | 输出**空间关系**而非像素或标签 | 否 | — | 变换/坐标/地点 | 🆕 此前整族遗漏（§7.5） |
| **H 内在分解与后期** | 改**光照/反光/阴影**这些成分 | 是 | **介于两者之间** | 派生新文件 | 🆕 此前整族遗漏，摄影后期核心 |
| **I 文档结构化** | 输出**结构**，不只是文字 | 否 | — | 版面/表格/数据 | 🆕 OCR 之外的遗漏（§7.5） |
| **J 学习式压缩** | 目标体积而非画质 | 是 | 否 | 更小的文件 | 🆕 此前遗漏；**先与传统编码对比**（§7.5） |
| **K 细粒度与属性** | 更细的分类粒度 | 否 | — | 标签 | ⚠️ 部分已被 A1/A2 含糊覆盖（§7.5） |
| **L RAW 域处理** | 在**去马赛克之前**的数据上算 | 是 | 否 | 派生新文件 | 🆕 此前遗漏（§7.5） |
| **M 垂直领域** | 医学 / 遥感 / 工业检测等 | — | — | — | **判不适用本项目**，仅列示分类学的完整性 |

共 **79 项**（按表格行数统计，2026-09-29 复盘补漏后）：A 18 · B 11 · C 12 · **D 8**（原 5 + 取证补 3）· E 6 · **F 4 · G 5 · H 5 · I 3 · J 1 · K 3 · L 3** = 79。其中 F–L 与 D6–D8 共 27 项是 §7.5 新增，**8 项标 ★**。

## 3. A 理解与分析类（18 项）

这是与"照片管理器"最贴的一类：不改原图、失败也无损、产物能直接进已有的标签体系。

| # | 能力 | 代表模型 | 典型体积 | 适配 | 说明 |
|---|------|---------|---------|------|------|
| A1 | 图像分类（封闭标签集） | MobileNetV3 / ConvNeXt-Tiny | 6–110 MB | ★ | 单前向、DirectML 友好。是 A17/E6 的地基 |
| A2 | **零样本打标** | CLIP ViT-B/32 | 181 MB (q4) ※ | ★ | **已在 M3 计划内**（Q15：DirectML 未测）。是本项目与产品本体最贴的一条 |
| A3 | 目标检测 | YOLO 系列 / RT-DETR | 6–70 MB | ★ | 未进 PRD。能给"图里有狗/车/建筑"级别标签，与 A2 互补（A2 判整体语义，A3 判具体物件） |

## 5. C 生成与编辑类（12 项）—— 判定：本地不做

**结论先给**：这一整类不进入本项目的模型清单，且在 M3/M4 的排期里也不该被提起来。理由不是效果，是架构级别的三座山：

1. **多步采样**：一次出图 = 15–50 次前向。u2netp 单次 21 ms，扩散一步几百 ms，一张图是 10–30 秒级——与本产品"点一下就出结果"的形态（§4.2 静默加载、D17 不置灰）直接冲突。
2. **显存**：UNet/DiT 主干 + 文本编码器 + VAE 同驻，连开发机 **8151 MiB 整卡**（K3）在生成 1024² 时都容易触顶——用户侧更低配的卡只会更早出局，所以这条不是"等换台机器就行"的问题。本项目已有"显存不足"分支（`GPU_MEMORY_LOW`），但那是兜底，不是运行常态。
3. **ONNX 导出与 DirectML 算子覆盖**：扩散管线的动态 shape 与自定义 attention 是 K2 上 `DmlFusedNode` 那类原生崩溃的高发区，而崩溃代价由子进程承担、由用户看见。

| # | 能力 | 代表模型 | 适配 | 判定理由 |
|---|------|---------|------|---------|
| C1 | 局部擦除重绘 inpainting | LaMa / MAT | **✗（有例外口子）** | **见下** |
| C2 | 画外扩展 outpainting | SD/FLUX outpaint | ✗ | 会"编造"用户没有的画面，与照片归档的真实性定位冲突 |
| C3 | 去水印 / 去路人 | SD inpaint 系 | ✗ | 撞 C1 的判定；去路人本质是 C1+主体保真，难度更高 |
| C4 | 指令式图像编辑 | FLUX.1 Kontext / Qwen-Image-Edit / InstructPix2Pix | ✗ | 体积（10 GB+ 级）与显存双撞 K3/K4；且属"改内容" |
| C5 | 可控生成（深度/姿态引导） | ControlNet | ✗ | 前提是已有 C 类主干 |
| C6 | 个性化主体生成 | LoRA / PhotoMaker / IP-Adapter | ✗ | 训练/微调不在产品形态内 |
| C7 | 换装 / 换背景 | ID-VTON 类 | ✗ | 同上；换背景已被 A8 抠图覆盖且无需生成 |

| C9 | 风格迁移 | AdaIN / 图生图 | ✗ | **判别式风格迁移（AdaIN 级）体积小、单前向，技术上不撞本节三座山**——判 ✗ 的依据是产品不是架构：属"玩一下"不属"整理照片"，PRD 里没位置 |

**C1 的例外口子（唯一的）**：`LaMa` 一系**结构上是判别式的 Fourier 同步卷积，不是扩散**，单前向、体积 ~200 MB、导出 ONNX 成熟。所以"擦掉一个固定物体"在技术上**可能**落在 B 类的安全区而不是 C 类的禁区。但两点保留意见：① 它擦完是"填平"，用户会期待"填对"，期待管理成本高；② 仍未在本机 DirectML 验证。故本地图把它记为 **C1-eval：允许单独探针，不等于放行**。

### 修正一处此前的技术路线表述

**D2「AI 生成图判别」** 原先写的路线是"专用检测器（纹理/频谱特征类）"。补查后改为**两条并列路线**，第二条更值得优先试：

1. 频谱 / 纹理伪影类检测器；
2. **利用 CFA 插值对 PRNU 传感器噪声相关性的影响，区分实拍图与计算机生成图**——属物理层痕迹，**比纹理特征更难被新一代生成模型绕过**。

### 这批补漏的实际结论（别误读成"要加很多模型"）

补上的 **27 项里只有 8 项标 ★**，而其中**成本最低的三条（G5 地标、K2 属性、K3 事件类型）全部是复用已经计划要下的 CLIP 编码器，零新增模型**。真正需要新模型的只有 H1 去反光、H2 去阴影、F1/F2 计算摄影、G4 地理定位这几条。

**换句话说：这次补漏的主要收益是让"词表与组合设计"变清楚了，而不是清单要膨胀。** 顺带确认了一件旧事——K3 与未决问题 Q11（打标词表从哪来）其实是同一个问题的两面。

>
> **✅ u2netp 已查（2026-09-29，链条如下）**
>
> - **一手来源是干净的**：原始官方仓库 `xuebinqin/U-2-Net`（作者 Xuebin Qin 等，CVPR 2020）**有 LICENSE 文件，类型 Apache License 2.0**——直接查看仓库文件清单确认。Apache-2.0 允许商用与再分发。

> - **同链条上更谨慎的一方**（rembg 是最广泛分发 `u2net.onnx` 的项目，其 issue #837 原文）：上游确为 `xuebinqin/U-2-Net` / Apache-2.0；但"**It does not cover the model files**"、"**I am not the rightsholder for those, so I cannot grant or confirm rights to them**"、"**I do not have a conversion record for that file**"，并建议"**If you need a verifiable chain of provenance, convert from the upstream checkpoint yourself**"；另明确指出离线交付时把模型打进包或引导下载属于"**redistributing them yourself**"。
> - **还有一处解释空间**：原仓库 README 对 `u2netp.pth` 只给 GoogleDrive / 百度网盘链接，**未单独声明权重许可**；仓库根的 Apache-2.0 是否延伸到托管在仓库外的权重文件，存在解释空间——这正是 rembg 维护者不敢替作者确认的原因。
>

3. **验能跑（K6 要求两组数字，不是两组里挑一组）**：本机真图端到端跑通，**DirectML 与 CPU 各测一次**，分别记录加载耗时、推理耗时、内存/显存增量。CPU 那组**必须先限 `intraOpNumThreads` 再测**（默认线程会吃满全部核心，M0 就是这么把机器压死的）。同时要用 **K7 那条 60 秒线**验一次：GPU 路径下推理超线，就该判 ✗ 或降为 ○。任一后端失败的处理分两种：GPU 侧失败 → 退回 ○ 或 ✗；仅 CPU 侧越线 → 条目放行、标 **「仅 GPU（本机 CPU 约需 N 分钟）」**，**按钮仍可点但有预计耗时与取消**（口径见 K6 第 3 条，不置灰）。
4. **进清单**：写入 `docs/design/ai-photo-processing.md` §4.3（带实测日期）与 `electron/ai/capabilityCatalog.ts`，并同步 sha256。

**CPU 兜底的铁律照旧**：任何 CPU 路径必须显式限 `intraOpNumThreads`。M0 探针没设它，10 分钟不结束、进程吃 6.3 GB、整机压到无响应。
