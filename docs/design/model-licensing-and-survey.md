# 模型许可准入与逐模型调研规范

> 建档 2026-09-29。触发点两条：① `v0.1.5` 已发布、GitHub 仓库公开，软件**此刻正在引导用户下载模型**，许可不再是"以后再说"的事；② 用户提出"我声明本软件仅供学习研究使用，是不是就避免了法律风险"——**答案是不能，详见 §2 第一条**，所以要把规则定在真正起作用的地方。
>
> 本文管三件事：**哪些模型可以进清单、要交出哪些证据、程序里怎么体现**。它配合 `image-model-capability-map.md` §8 的四步流程使用（本文在其中插入一步），不替代 §4.3 那条"只有实测跑通才能进 UI"。

---

## 1. 一句话结论

**许可风险落在"分发行为"，不落在"用户拿软件做出什么图"。** 所以要管的是**我们从哪里拿到权重、凭什么再分发**，而不是在界面上加一句免责声明。

---

## 2. 三条基本裁定

### 裁定一：「本软件仅供学习研究使用」**不能免除分发风险**

理由三层，任一层单独成立这句话就无效：

1. **限制不由我们的声明解除。** 能解除"不得商用/不得再分发"的只有两种：**权利人授权**，或符合法律规定的例外。后者通常覆盖**使用者本人学习使用**，一般**不覆盖**"向不特定公众分发他人训练出的权重副本"这一动作。
2. **对本项目当前的对象根本用不上。** u2netp 是 **Apache-2.0**，本来就允许商用与再分发（见 `image-model-capability-map.md` §8 已查链条）。给它戴"学习研究"的帽子，是解决一个不存在的问题，还会**误导用户**以为不能商用。
3. **它可能与事实自相矛盾。** 本项目公开发布、作者运营个人接单站、软件作为作品对外呈现。若实际带有商业性质，这句声明就成了**我们自己不会遵守的条款**——不但不护身，还伤可信度。

**它的正当用途只有一个**：**告知**——"本软件会下载这些第三方模型，各自许可如下，请你自己遵守"。约束对象是**用户行为**，不是**我们的分发责任**。

**只有一种情况它才有对应目标**：引入带**非商用（NC）**条款的模型时。但那时限制来自上游，且声明必须与"软件本身非营利"一致。**正确策略是从一开始就不引入 NC 模型**，而不是指望声明兜底。

### 裁定二：代码许可 ≠ 权重许可

常见做法是代码一个许可、权重另一套。**只看仓库根目录 LICENSE 会得出错误结论**，必须看模型卡/权重自身的声明。权重托管在仓库外（网盘、对象存储）时，仓库根的 LICENSE 是否延伸到它，存在解释空间——遇到这种就按"证据不足"处理，不按"应该可以"处理。

### 裁定三：转导出的 ONNX 必须披露来源差异

Apache-2.0 要求再分发时保留版权与许可声明、**并注明修改**。我们的权重几乎都来自第三方转导出（ONNX 版），**"这是转导出的、非上游作者一手发布"属于必须写进 NOTICE 的内容**，不是可选说明。

## 3. 准入规则（三档）

### 3.0 许可白名单（2026-09-29 用户裁定，目的是**取消逐次评估**）

**只允许以下 SPDX 标识进清单**：`MIT`、`Apache-2.0`、`BSD-2-Clause`、`BSD-3-Clause`、`ISC`。

- **名单外一律不引入、不评估、不讨论**——包括任何带 NC / 非商业 / 仅研究 / SA / 相同方式共享 / "数据不得用于训练"字样的许可。
- 这条的作用不是更安全，而是**把"每次都要请人判断"变成"看一眼标签就决定"**。逐次评估的成本才是这个问题真正麻烦的地方。
- 拿不到明确 SPDX 标识、或许可写不清的 → 直接按「不列」处理，**不进入讨论环节**。

> **⚠️ 下面 §3.1 的改判不放松本节。** 白名单仍然是第一道、也是最硬的一道闸；改判只发生在"标识已经在白名单内、但 LICENSE 文件本体找不到"这一步。

### 3.1 三档判定（2026-09-29 改判：找不到 LICENSE 文件本体时默认按可用处理）

**改判内容**（用户裁定）：判据②原先要求"权重与 LICENSE 文件必须同仓"，实测下来**几乎所有可用的 ONNX 镜像仓都只有 README 里的 `license:` 字段、没有 LICENSE 文件本体**（MODNet / BiRefNet / MediaPipe / silueta / u2net 人像版六个仓全部如此，唯一例外是 `opencv/` 系列）。这条判据的实际效果是**把整条升级路线堵死**，于是改为：

| 档 | 条件 | 处置 |
|----|------|------|
| **可用** | ① 许可标识在 §3.0 白名单内；② **权重与 LICENSE 同仓**（最理想）；③ 一手权利人发布，**或**我们自己从一手权重重转并有完整记录 | 可进清单、可进安装包、可引导下载。附许可全文与归属声明。 |
| **可用（附披露）** | 许可标识在白名单内，但 **LICENSE 文件本体找不到**（只有 README 自称）→ 按 §3.1.1 记来源后**视同可用** | 同上，但卷宗与 NOTICE 必须写明"许可依据为上游仓库 README 自称的 SPDX 标识，未见 LICENSE 文件本体"。 |
| **需评估** | 许可标识在白名单内，但**同一性靠别人担保**（第三方转导出的 ONNX、无转换记录） | **允许新增**（2026-09-29 取消原「不得新增此档条目」），但必须挂 `provenanceStatus` + §6.1 那四行已知限制记录，**逐条点名**，不得写成允许所有条目为空。 |
| **不列** | 许可标识**不在**白名单；或标识缺失/写不清；或上游明确禁止再分发 | **不进清单、不进界面、不进安装包**，也不做"引导用户去下载"。 |

**这次改判保住了什么（四条红线，一条都不能再让）**：

1. **白名单本身不动**。GPL / AGPL / LGPL / CC-BY-NC / "仅研究" / 无标识 → 仍然一律不列。改判只影响"标识合规、文件缺失"这一格。
2. **"找不到"指的是查过之后没有，不是"没去查"**。必须留下可复现的查询证据（文件清单原文 + 日期），否则按标识缺失处理 = 不列。
3. **裁定三不变**：转导出的 ONNX 必须在 NOTICE 里写明"系第三方转导出、非上游一手发布"。披露义务一条没减。
4. **新增条目必须自带 `provenanceStatus` + §6.1 四行记录**。取消的是"不许新增"，不是"可以裸进"。

**为什么这样切仍然够用**：真正决定风险的从来不是"仓库里有没有那个文件"，而是**许可类型允不允许我们再分发**。Apache-2.0 的权重，镜像仓少附一份 LICENSE 正文，缺的是**我们的留存动作**（把全文抓下来存进 `LICENSES/third-party/` 即可补齐），不是授权本身。而 GPL/NC 那一类，无论文件在不在都不能用——所以白名单这道闸保留着，风险就还在可控范围内。

**推论（要接受）**：一手作者仓库若把权重放在仓库外（如 `xuebinqin/U-2-Net` 用 GoogleDrive/百度网盘），它**只作出处与归属来源，不作分发来源**。⚠️ 注意 MODNet 也是这一类：一手仓 `ZHKKKe/MODNet` 全树 48 个文件里**只有 LICENSE、没有任何权重**，也没有带资产的 release（2026-09-29 实测）。

#### 3.1.1 「找不到 LICENSE 文件本体」要留下什么才算查过

改判之后，"找不到"成了一个**放行理由**，所以它必须可复核——否则就退化成"没查也算查"。四件事缺一不可：

```
① 查询方式与日期：调 HF API `?blobs=true` 取 siblings 原文（或 ModelScope 文件树），记当天日期
② 文件清单原文：把 siblings 列表贴进卷宗的许可小节，让人能一眼看出"确实没有 LICENSE 那一项"
③ 标识出处：README 里的 `license:` 字段值（或 ModelScope 的 LicenseName），并注明它是自填元数据、非核验值
④ 补洞动作：把上游一手仓库的许可**全文**抓下来存进 `LICENSES/third-party/<model>.txt`
```

第 ④ 项是这次改判的**代价**，不是可选项：既然不再要求上游仓库附 LICENSE 文件，那这份全文就得由我们留存，否则 §5 待办 ② 的 NOTICE 就没有内容可写。**做了 ①②③ 而不做 ④，等于把改判当成免查。**

## 4. 一条模型算"查过"，必须交出这些证据

缺任何一项就记为**未查**，不许写"已核实"：

```
1. SPDX 许可标识                     例：Apache-2.0
2. LICENSE 文件是否真实在仓库内        是 / 否（查文件清单，不看 README）
3. 一手 or 二手                       一手=权利人发布；二手=第三方转导出
4. 转换记录 / 可复现性                 能否从上游权重复现出同一份文件
5. sha256 + 体积                      双源都要查（hf-mirror 与 ModelScope）
6. 本机 DirectML 跑通记录              真图、耗时、显存与内存增量
7. 归属材料                           原作者、论文、上游仓库链接
```

第 5、6 项沿用既有口径（**双源查 `?blobs=true` 的真实体积**，防 LFS 空壳；**逐个实测**，防"文件能下 ≠ 功能可用"）。

## 5. 程序里怎么体现（五处）

| # | 落点 | 内容 | 状态 |
|---|------|------|------|
| 1 | 仓库根 `LICENSE` | 本项目自己的许可全文。**2026-09-30 落地，但不是 MIT**：改为「源码公开非商业使用许可 v1.0」，`package.json:7` 同步为 `SEE LICENSE IN LICENSE`，界面与 README 撤掉"开源"措辞 | ✅ 已做 |
| 2 | `LICENSES/third-party/` + `NOTICE` | 每个模型的许可全文 + 归属，并写明"系第三方转导出，非上游一手发布" | ✅ 已做（2026-09-30）：两份一手仓 LICENSE 逐字留存 + `LICENSES/third-party/README.md` 记取源；`NOTICE` 由 `scripts/gen-notice.cjs` **从清单生成**（不手写，避免第二份副本漂移），并已进 `build.files` 随包分发 |
| 3 | 设置或"关于"页「第三方模型与许可」只读清单 | 模型名 / 许可 / 上游来源 / 用途 / 归属 | ❌ 未做 |
| 4 | 模型下载确认文案 | 一句许可摘要，如"该模型以 Apache-2.0 提供，版权归原作者" | ❌ 未做 |
| 5 | **断言** | 清单里每条模型必须有非空 `license` 与 `provenance`，缺则**测试失败** | ✅ 已做（2026-09-30）：`tests/modelLicense.test.ts` 九条，含"标识必须在白名单内""留存文件必须存在且正文与标识对得上""NOTICE 必须与清单同步"；两条反证已实测会红（改坏文件名 / 改 sha256 不重跑 notice） |

**2026-09-30 修订（第 1 行落地时）**：

- 本项目自己的许可改成了**非商业**，这与 §2 裁定一**不矛盾**：裁定一否掉的是"用『仅供学习研究』这句话给**第三方模型权重的再分发**免责"——那条例由权利人授权决定，我们说了不算；本次是对**自己写的代码**主张权利，著作权在我们手里，禁止商用是作者的本权。两条别混着引用。
- 界面那句「此项目仅供学习交流使用，严禁用于商业用途，请在 24 小时之内删除」现在有了对应的法律文本（`LICENSE` 第 3 条），**不再是那句被否掉的免责语**。其中"24 小时之内删除"已于 2026-09-30 写成 `LICENSE` **3.7**：只约束复制与留存、不约束这 24 小时内的使用，并如实声明本软件不设到期自动失效之类的技术手段——这一款靠许可约定生效，不靠强制力。
- 新许可 §4 已对外写明第三方组件的许可可查。**第 2 行已于 2026-09-30 兑付**：两份一手仓 LICENSE 逐字留存、`NOTICE` 由 `scripts/gen-notice.cjs` 从清单生成、三项都进了 `build.files`。§4 措辞同时按实测校准成两条不同路径——代码依赖的正文随包内 `node_modules/<包>/LICENSE` 分发（实测 v0.1.5 包内 98 份），只有模型权重的正文存在 `LICENSES/third-party/` 并写进 `NOTICE`；把它们混成一句就会写成我们兑现不了的承诺。**第 3 行（界面「第三方模型与许可」只读清单）仍未做**，是这条承诺里剩下的缺口。

**第 5 项是关键**。本项目的经验已经证明机制比提醒有效：那条"AI 设置分区零 `input`"的断言之所以真挡住东西，是因为**它会失败**。靠文档提醒会漂移，靠断言不会。

**数据源必须单一**：许可与来源信息只写在 `electron/ai/capabilityCatalog.ts` 的条目字段里，界面清单和 NOTICE 都从同一处读。**不在两处维护同一事实**（与项目已定的"跨组件复用的句子进一处"同口径）。

## 6. 存量条目怎么办（u2netp 的显式处理）

规则若不能解释现实就是空规则，所以这里写死：

- **u2netp 现状（2026-09-29 按 README 全文校准过定性）**：
  - **授权类型这一环是通的**：一手仓库 `xuebinqin/U-2-Net` 确有 Apache-2.0 的 LICENSE 文件；二手上传者也在 README 里**明确指回原作者**，并写明"采用 Apache-2.0 是为了与原模型一致"——属于**沿用上游许可并如实标注**，不是自我授权。
  - **唯一真缺口是「同一性」**：README 没有**转换脚本、源 `.pth` 的文件名或哈希、转换日期**，所以"我们手上这份 `.onnx` 就是作者那份权重的忠实转换"**无法验证**。这与 rembg 维护者自陈的"我没有那份文件的转换记录"是同一性质问题。
  - 另有**许可副本**缺口（该仓库未附 LICENSE 文件本体，而 Apache 要求随分发附全文）——这是**上游镜像不规范**，不是本项目的错，但它正说明本文 §5 待办 ①② 为什么必须做。
  - **⚠️ 分清两个"同一性"**：`capabilityCatalog.ts:84` 的 `sha256` 只保证"我们机器上的文件与清单写的那份字节一致"，**不保证"那份文件来自原作者"**。前者是完整性校验，后者才是来源链，本项目目前只有前者。
  - **风险性质**：属**供应链完整性**风险（无法排除权重被替换/改动），**不是版权风险**；实际危害等级评为**低**。
- **档位维持「需评估」不放宽**：三条判据（非一手、非自转、该仓库无 LICENSE 文件本体）确实不满足。**结论变软不等于放松规则**，否则规则就成装饰。
- **处置**：**允许继续留在清单**（它已发布、能跑、许可类型无问题），但必须：
  1. 在该条目上挂 `provenanceStatus: 'second-hand'`；
  2. 第 5 项的断言对**该值给出显式豁免并写明原因**——豁免要**点名到这一条**，不得写成"允许所有条目为空"，否则就造出了一个永不失败的假断言；
  3. **记为已知限制并明确接受，不整改**（2026-09-29 用户裁定）。理由写实：自转导出需要装 PyTorch 级依赖（数百 MB 至 2 GB），而这一环出错的最坏后果是**抠图效果与预期不同**，不是被追责——**收益不抵成本**。
- **新增条目照同一套规矩走**（2026-09-29 随 §3.1 改判同步）：许可标识须过 §3.0 白名单，且必须自带 `provenanceStatus` + §6.1 那四行已知限制记录才允许进清单。**不再因"LICENSE 文件本体缺失"被挡**，但披露与留存义务（§3.1.1 第 ④ 项）一条不减。首个按新规矩进来的条目是 MODNet，见 [`../models/modnet.md`](../models/modnet.md)。

### 6.1 「已知限制」记录怎么写（§3.1 需评估档引用的就是这个）

需评估档不是"待办"，而是**一笔明确接受的风险**，所以要写清四行，写完就结案，不许长期挂着：

```
缺口：        哪一环依赖别人（例：同一性——第三方转导出，无转换记录）
谁担保：      该环节的实际担保方（例：BritishWerewolf 仓库，个人账号，无转换记录）
最坏后果：    这一环出错会怎样（例：掩码效果与作者版本不同；非版权追责）
复查触发条件：什么情况下重新看这条（例：抠图效果出现无法解释的异常 / 换用新模型时）
```

**没有这四行，"需评估"就会变成一个永远不关闭的状态。** 这是本规范里最容易写成空话的一处，所以固定成模板。

### 关于 ModelScope 的许可字段（2026-09-29 实测，务必看这条）

上面三个仓库在 ModelScope 上的返回元数据**完全一致**：

```
CreatedBy: Cherrytest（昵称"小橙鱼"）    ModelSource: USER_UPLOAD    FromSite: maas
LicenseName: ""    LicenseLink: ""
```

也就是说：**ModelScope 上这些命名空间照抄 HF 的 `onnx-community/`、`Xenova/` 仓库，其实是同一个第三方批量搬运**，而 HF 那边的 author 是 `onnx-community` / `Xenova` 本身。搬运**不改变授权**，但多了一个无法核验的环节；且 ModelScope 只存一个许可**字符串**，既没有正文也没有链接，字段还**不强制**（CLIP 那条就是空的）。

**结论**：ModelScope 的价值是**下载通道**（本机实测免代理直连约 2.8 MB/s、支持 Range 续传，而同期 hf-mirror 直连超时），**不是许可来源**。按已定裁定它只是**并列第二源、不替换 hf-mirror**。许可与文件清单一律以**上游一手仓库**为准；从 ModelScope 下载还必须补做**与 HF 的 sha256 比对**——搬运内容是否逐字节一致，本项目至今**一次都没验过**。

**队列纪律**：一次只查一个，查完就把 §4 那七项证据填进 §10 的模板并附来源日期。**不许凭印象填**。

## 9. 许可之外的两条边界

1. **生物特征**：人脸检测、人脸修复处理的是人脸信息，那不归模型许可管，归个人信息保护类法规管。本项目的"纯本地推理、图像不出机器"（K1/K5）是显著有利因素，但仍应在隐私说明里**主动写明人脸数据的处理方式**。⚠️ 一旦允许配置代理（U7），"不上传照片内容"这句仍成立，但**绝不能**写成"不走网络、不经过任何第三方"。
2. **这不是法律意见**。本文是工程与来源核查层面的规则；§6 那个解释空间、以及"能否引导用户下载 NC 模型"这类问题，无法靠我们自己消除。要绝对稳妥需找知识产权法务确认。
