## 1. 背景

PhotoTagManager 现在只做两件事：发现图片、把标签写进图片 XMP。用户在浏览到一张照片后，如果想对它做任何处理（抠图、修脸、变清晰），必须退出本应用、打开别的软件、处理完再导回来重新扫描。

本设计要在这个断点上接一段能力：**在预览界面里直接对当前照片发起一次 AI 处理，结果作为派生文件落回原目录，并自动带上标签。**

## 2. 目标与非目标

### 2.1 目标

| # | 目标 | 说明 |
|---|------|------|
| AG1 | 处理不出机器 | 全部推理在本机完成，照片内容不上传任何第三方服务 |
| AG2 | 代价先于效果可见 | 用户在点"下载"和"执行"之前，就知道这次要花多少磁盘、多少显存、大致多久 |
| AG3 | 原图永不被改 | AI 处理不产生任何不可逆操作，用户随时可删派生文件回到起点 |
| AG4 | 不破坏"文件是主数据" | 派生文件是普通图片文件，靠已有扫描机制被发现，不引入需要长期维护的中心数据库 |

### 2.2 非目标（本设计明确不做）

- **不做对话式 AI / 提示词生图**。本产品是图片管理器，"文生图""对话改图"会引入完全不同的交互范式和体量级得多的模型，另案。
- **不做实时预览**（拖动滑块→画面实时变化）。**理由不是"推理慢"**——M0 实测单次推理仅 21ms。真正的原因是：一次完整处理还要叠加预处理、跨进程传图、图像编解码，且未加载模型时还要 1~3 秒加载；而拖动滑块会让同一张图被反复推理几十次，代价与延迟都不可控。所以仍是"点执行 → 等一下 → 看结果"。
- **不做视频**。
- **不做模型训练/微调**，只做现成模型的下载与推理。
- **不做云端 API 兜底路线**（见 D5）。

## 3. 关键设计决策

| 编号 | 决策 | 理由与后果 |
|------|------|-----------|
| **D5** | **推理位置：纯本地** | 用户 2026-09-23 明确选定，放弃云端 API 路线。**后果**：必须自建模型下载与磁盘管理；8GB 显存构成硬上限；首次使用要等下载——实测 hf-mirror 下载速率 **1.27 MB/s**（213.6MB 用 168.8s）到 **0.39 MB/s**（4.36MB 用 11.3s，小文件受握手开销拖累），即一个 100MB 模型约需 1~4 分钟，必须做成可中断、可续传、进度可见的。**代价**：放弃云端更强的效果与零下载的实现便利 |
| **D6** | **结果落地：同目录派生新文件** | 输出写到原图旁边 `原名.<action>.<ext>`，原图本体字节不变。**理由**：与本项目"标签跟文件"的迁移性一致——派生文件带着继承的标签，复制到别处仍然自描述；且完全可逆。**后果**：目录里会多出文件、占磁盘；派生文件会被下一次扫描发现并出现在网格中（这是期望行为，不另建"成果库"） |
| **D7** | **三层分离：行为 → 模型 → 运行时** | 用户看到的是"抠图""美颜"这种行为；行为下挂 1~3 个候选模型；模型底下才是真正的推理引擎。三层各自可独立增删。**理由**：模型生态换得快（今年好用的分割模型明年可能被替换），而"抠图"这个需求十年不变。把易变的部分压在中间层，UI 和 IPC 契约就不会随模型改动而震荡 |
| **D8** | **加载是显式动作，但代价是秒级，不是分钟级** | 「已下载」与「已加载」仍是两个要区分显示的状态，但 M0 实测把这条的 UX 影响降级了：u2netp（4.4MB）加载 **0.96s**、推理 **21ms**（DirectML）；换到 213MB 的模型加载 **3.14s**。所以加载**不需要进度条、不需要可取消**，一个转圈图标足够。<br>**显存**：一次 u2netp 推理使整卡显存从 853 → 1178 MiB（**Δ325 MiB**，口径是整卡 `nvidia-smi memory.used`，含其他进程，非本应用独占）。相对 8151 MiB 总量，同时驻留 3~4 个这类模型在数字上是宽松的，但大模型的激活占用会随输入分辨率涨，**仍按"一次只驻留一个"设计**，等 §4.3 清单里的模型逐个测过再考虑放宽 |
| **D9** | **推理跑在独立子进程，不在主进程** | 原生推理库是 C++ 代码，失败方式是**进程级崩溃**。**这条已被实测证实不是理论担忧**：BiRefNet-lite 在 DirectML 上加载成功，但一执行就抛 `DmlFusedNode_19_64` 原生错误（ONNX Runtime 的 `sequential_executor.cc` 直接返回非零状态）。这类错误发生在主进程就等于一张坏照片干掉整个窗口，用户连带丢失正在进行的批量打标。**后果**：图像数据要跨进程传递，多一次序列化开销（未实测，但相对 21ms 的推理时间可忽略）；需要子进程生死与重启管理 |
| **D10** | **派生文件继承原图标签 + 追加行为标签** | 抠图产出的文件自动带上原图的 `XMP-ptm:Tags`，再加一个行为标签（如 `AI抠图`）。**理由**：否则派生文件会脱离用户已有的标签体系，筛选时被孤立；行为标签则让"所有 AI 产物"可被一键筛出与批量清理 |
| **D11** | **引擎 = `onnxruntime-node` 的 DirectML 后端；不做插件，随包分发** | M0 实测：DirectML 在本机 RTX 5060（Blackwell）上可用；同一模型同一输入连跑三次 CPU 约 201ms、DirectML 为 20/8/7ms，**约快 10~29 倍**（区间是波动，不取单点）。CUDA 后端在 npm 预编译包里**根本不存在**（`backend not found`）；`ort-web` 的 WebGPU 后端在 Electron 31 里**会话创建死锁**（连 4.4MB 模型 180s 不返回；注意 WebGPU 本身可用，死的是 ort-web 这层）。<br>**推翻 v0.1 的体积估算**：v0.1 按 npm 报的 `unpackedSize=301MB` 推出"安装包翻倍、所以必须做插件"，这条链是错的——287MB 落盘里含 darwin/arm64 85MB、win32/arm64 69MB、linux 两平台 92MB，本项目只发 Windows x64。**真正要带的只有 `bin/napi-v6/win32/x64` = 64.0 MB**（onnxruntime.dll 27.4 + DirectML 17.7 + dxcompiler 17.2 + dxil 1.4 + 绑定 0.3）。安装包 89.8 → 约 115 MB，安装后 352 → 约 416 MB（+18%）。**为 18% 引入插件机制（双安装包发版矩阵、杀软对运行时落地 DLL 的误报、引擎版本与 Electron 升级绑死）不划算**，故随包分发 + 打包时裁掉其他平台目录 |
| **D12** | **CPU 后端必须显式限制线程数** | 实测事故：213MB 模型走 CPU 后端且未设 `intraOpNumThreads` 时，ONNX Runtime 默认占满本机 32 个逻辑核，10 分钟不结束、单进程吃 **6.3GB** 内存，**把开发机压到无响应**。因此任何 CPU 兜底路径都要显式限核（默认建议 2~4，实施时定），并在界面上明确标出"当前走 CPU，会慢很多"，不允许无声降级 |

## 4. 功能设计

### 4.1 入口

预览界面（全屏大图）底部标签行的右侧，增加一个「AI 处理」按钮。点击后从右侧滑出面板，**悬浮在大图之上**，可拖拽边缘改变宽度，可随时关闭。

**为什么是抽屉而不是对话框**：现有预览界面已有顶栏（路径/翻页/定位/复制）与底栏（标签/信息），中部整块都是大图。弹窗会盖住正在处理的图，而"处理前/处理后"的对比是这项功能的核心体验——面板必须能收起，让位给大图本身。

**为什么不做在缩略图网格上**：网格是多选批量场景。推理本身很快（实测 21ms），所以瓶颈不在算力，而在**产物**——批量跑 100 张就是 100 个新文件占磁盘，而抠图这类结果必须人逐张看一眼才知道对不对，成批产出错误结果等于成批垃圾文件。批量入口留到 M4，且必须先有队列、失败清单与磁盘预估才开放。

### 4.2 面板内的工作流

```
选行为  →  选模型（带代价）  →  下载（如需）  →  加载（如需）  →  执行  →  看结果 → 保存 / 丢弃
   ↑                                                                          │
   └────────────────────────────── 换行为，重新走一遍 ←──────────────────────────┘
```

**第一屏是行为列表，不是模型列表。** 每行一个行为，右侧显示该行为下"当前默认模型"的名字与状态徽标。用户不关心 BiRefNet 还是 U²-Net，只关心"能不能把背景抠干净"。

**模型选择收在二级**：点开某个行为才展开它的候选模型。每个模型条目上必须直接显示四个代价字段——下载体积、落盘占用、显存需求（够不够）、单次耗时。**这四个值全部来自清单里的实测记录**：没在 DirectML 上真跑通过的模型不允许进清单（见 §4.3 的硬规则），界面上也就不该出现"未测定"这种占位。

**状态徽标**（同一时刻每个模型只有一个状态）：

| 状态 | 可用操作 |
|------|---------|
| 未下载 | 下载 |
| 下载中 | 取消（进度可见，支持断点续传） |
| 已下载·未加载 | 加载 / 删除（回收磁盘） |
| 已加载·空闲 | 执行 / 卸载（释放显存） |
| 推理中 | 取消 |
| 不可用 | 无操作，显示原因（磁盘不足 / 无可用加速设备 / 校验失败） |

### 4.3 行为与模型清单（含 DirectML 实测状态）

体积与路径来自 2026-09-23 对 `hf-mirror.com` API 的实际查询；"DirectML 实测"列来自同日在真机上的加载与推理验证（命令见附录 B）。

| 行为 | 面向用户的说法 | 候选模型 | 下载体积 | DirectML 实测 | 阶段 |
|------|--------------|---------|---------|--------------|------|
| **人像抠图** | 去除人像背景 | U²-Netp | **4.4 MB** | ✅ **已跑通**：加载 0.96s、推理 21ms、产出真实透明 PNG | **M1** |
| 通用抠图 | 去除任意主体背景 | BiRefNet-lite（fp32） | 214 MB | ❌ **加载成功 3.14s，推理报 `DmlFusedNode` 原生错误** | M3，需换模型（Q14） |
| 通用抠图 | 同上 | BiRefNet-lite（fp16） | 109 MB | ⛔ 未测。且 fp16 路径在本环境另有风险 | M3，待测 |
| 智能打标 | 自动建议标签 | CLIP ViT-B/32（q4） | 181 MB | ⛔ 未测（仅确认文件存在） | M3（Q15） |
| 人脸修复 | 老照片 / 低清人脸清晰化 | GFPGANv1.4（onnx） | 325 MB | ⛔ 未测 | M3 |
| 深度图 | 背景虚化 / 景深 | Depth Anything V2 small（int8） | 26 MB | ⛔ 未测 | M3 可选 |
| 美颜 | 磨皮 / 五官微调 | 待选 | — | ⛔ 无源 | M3（Q10） |
| 超分 | 放大变清晰 | — | — | — | **不进清单**（Q12），见下 |
| 可编辑抠图 | 手动补选区域 | SAM ViT-B（quantized） | 101 MB | ⛔ 未测 | M4 |

**新增硬规则：只有「已跑通」的条目才能出现在用户界面里。** M0 的教训是——同一个引擎上 u2netp 跑得漂亮、BiRefNet 一执行就崩。"仓库里有这个文件"和"这个功能可用"之间没有任何必然联系，清单不能靠查 API 体积来成立。

**为什么 M1 首个行为叫「人像抠图」而不是「抠图」**：U²-Netp 是人像 matting 模型。探针拿一张演唱会现场照测，它把舞台亮部当成了主体（前景占比 8.7%，轮廓连贯但完全选错对象）。链路与性能都是真的，**通用性不是**。所以 M1 对用户就写"人像抠图"，通用抠图留到 Q14 测出可用的模型再开。

**为什么超分不进清单**：镜像上名为 `Real-ESRGAN-ONNX` 的社区仓库，其 `model.onnx` 实际大小是 **0.0 MB**——那是未解析的 Git LFS 指针文件。写进清单就会出现一条"永远下不动"的条目，且下载器会把它当成一个几十字节的成功文件。**可信源找到之前，超分不承诺。**

**为什么 M1 只带「人像抠图」这一个行为**：

- 它是目前**唯一在 DirectML 上真跑通、有实测耗时和真实产物**的一条。M1 的任务是把骨架（清单 / 下载续传 / 加载 / 派生文件 / 标签继承 / 丢弃 / 崩溃恢复）做完做稳，骨架不该和"某个模型到底能不能用"绑在一起验证。
- 智能打标虽然和业务本体最贴（能直接复用已经跑通并测过的 `tags:write-image` 链路，零新存储），但 **CLIP 从未在本环境跑过**（Q15）。它值得做，但要带着实测记录进 M3。
- 美颜是两段式流水线（先人脸检测定位，再对人脸区域修复），拿它当第一个行为会把"链路通不通"和"效果好不好"混在一起测，失败时分不清是下载、加载、推理还是落盘的问题。

### 4.4 派生文件的命名与内容

| 行为 | 输出文件名 | 容器格式 | 为什么 |
|------|-----------|---------|--------|
| 人像抠图 | `原名.cutout.png` | PNG | 必须带 alpha 通道，JPEG 会丢透明度 |
| 美颜 | `原名.beauty.jpg` | JPEG | 质量参数默认值**待 M3 实施时定**，不预设 |
| 人脸修复 | `原名.restore.jpg` | JPEG | 同上 |
| 智能打标 | **不产生新文件** | — | 直接写原图 XMP |

派生文件写入元数据：继承原图全部 `XMP-ptm:Tags` + 追加行为标签 + 保留拍摄时间等原始 EXIF（用现有 exiftool 通道复制，不重新编码元数据）。

**同名冲突**：`原名.cutout.png` 已存在时不覆盖，改用 `原名.cutout.2.png`，并在界面上说明为什么多了一个序号——用户必须能预期文件名怎么来的。

### 4.5 结果查看与撤销

执行完成后，面板内显示"处理前 / 处理后"双栏对比，并提供三个动作：

- **保存**：派生文件正式留在目录里（实际上文件已写盘，"保存"是指停止"待确认"态并提示可去资源管理器查看）
- **丢弃**：删除刚生成的派生文件，目录回到处理前
- **替换原图**：**不提供**。要用户自己去资源管理器操作，本应用不做不可逆动作（AG3）

## 5. 磁盘与显存管理

### 5.1 磁盘

- 模型文件存放于应用数据目录下的独立子目录，与原图目录完全分离，不与缩略图缓存混放。
- 面板顶部常驻一行「模型占用 X GB · 可用磁盘 Y GB」。C 盘当前剩 247 GB（实测），但用户可能在别的盘，需运行时读取。
- 下载前预估：`(模型体积) > (可用磁盘 - 安全余量)` 时直接拒绝并说明，不允许下到一半写满磁盘。**安全余量仍未实测**——M0 没有覆盖磁盘写入这一项。实施时按「模型体积 + 一份派生图峰值」来取，定下来之前界面上不显示"预计还需 X"这类推断。
- 删除模型必须同时清掉临时文件与索引记录，不留孤儿。

### 5.2 显存与并发

- 同一时刻**只允许一个推理任务在跑**，其余排队。首版不做并发调度。
- 面板显示「已用显存 / 总量」（本机实测总量 8151 MiB）。**口径必须标注清楚**：探针能拿到的是整卡 `memory.used`（一次 u2netp 推理 Δ325 MiB，但含机器上其他 GPU 进程），拿不到分进程显存（`nvidia-smi --query-compute-apps` 在本机驱动返回 `[N/A]`）。所以界面应显示"整卡已用"而不是谎称"AI 占用了多少"。
- 加载新模型导致显存不足时：明确报"显存不足，请先卸载 XX"并给一键卸载，**不静默换 CPU 跑**。实测代价差距是 CPU 201ms 对 DirectML 21ms（u2netp，约 10 倍；模型越大差距越大），无声降级会让用户以为程序卡住。若提供"改用 CPU"选项，必须是用户显式勾选，且按 D12 限线程。
- 空闲卸载：加载后连续空闲一段时间自动卸载。现在有了依据——加载一次是 0.96s（4.4MB）到 3.14s（213MB），代价很小，**所以自动卸载可以激进一些**（倾向"宁可让用户多点一次加载"），具体时长在实施时按这个量级定，不再是未知数。

## 6. 失败与边界

| 场景 | 表现 | 为什么这样 |
|------|------|-----------|
| 下载中断 | 保留 `.part` 断点，重开可续传 | 实测 hf-mirror 持续下载 **1.27 MB/s**（213.6MB 用 168.8s），一个百 MB 级模型要两三分钟，重头下不可接受 |
| 校验失败（sha256 不符） | 删除文件、报"下载内容损坏，请重试" | 静默用坏文件会在推理阶段崩得莫名其妙 |
| 子进程崩溃 | 主进程感知并重启子进程，当前任务标失败并提示重试 | 用户不能因为一张坏图丢窗口（D9 的全部理由） |
| 显存不足 | 见 5.2 | |
| 原图过大（超模型输入上限） | 处理前按模型规格自动降采样，并在界面注明"已在 NxN 下处理" | 不降采样会直接崩；不注明则用户以为是模型效果差 |
| RAW / HEIC 输入 | 先转码为模型可吃的格式再处理，转码中间文件用完即删 | 现有代码已记录 RAW/HEIC 写 XMP 可能不被 exiftool 支持，输入侧同样要防 |
| GIF / 多帧图 | 明确拒绝，只处理首帧或提示不支持 | 抠图多帧 GIF 的产物形态没有共识，别猜 |
| 磁盘写满 | 中止、回滚已写的派生文件、报剩余空间 | |
| 无可用 GPU 加速设备 | 清单里所有条目转「不可用」并说明原因，允许显式选择 CPU 慢速模式 | 不能让用户面对一片没有任何解释的灰按钮 |

## 8. M1 验收

以下每条都要在真实构建产物上手动走一遍，不看单测绿灯当交付（M0 探针与 typecheck/test 是证据的一部分，不覆盖行为正确性）：

1. 全新环境（`userData` 下模型目录为空）打开面板 → 「人像抠图」显示「未下载」，体积显示 **4.4 MB**。
2. 点下载 → 进度条推进 → 中断应用重启 → 再次下载从断点继续，不从头开始。
3. 下载完成 → 状态变「已下载·未加载」→ 磁盘上文件 sha256 与清单一致。
4. 点加载 → 状态变「已加载·空闲」，**约 1 秒内完成**（M0 实测 0.96s；若实测到分钟级说明实现有问题，不是模型变了）。加载期间不出现进度条也属预期。
5. 点执行 → 完成后同目录出现 `原名.cutout.png`，**原图字节未变**（比对 mtime 与 sha256）；推理耗时与 M0 实测的 21ms 同量级（含跨进程传递与图像编解码，允许是它的若干倍，但不应到秒级）。
6. 派生文件透明区域正确：**压到品红底上验证**（渲染器会把透明显示成白底，看白底判断不了），背景透出、主体边缘连贯。
7. **能力边界**：用一张人像照与一张非人像照（如风景/演出）各跑一次。前者应抠对；后者**允许选错主体，但不得崩溃、不得报未知错误**，且界面文案不得承诺"去除任意背景"。
8. 派生文件带原图全部标签 + `AI人像抠图` 标签；重新扫描后它能被该标签筛出。
9. 点丢弃 → 派生文件消失，目录回到处理前状态。
10. 面板首屏**只出现「人像抠图」一个行为**，没有任何"点了提示不可用"的死条目——未实测的行为与模型一律不进 UI，而不是灰着显示。
11. 强制 CPU 模式 → 界面明确说明当前走 CPU 及其代价；**任务管理器可见 CPU 占用被限制在设定的核数内，不允许占满全部核心**（D12 的直接验收，探针阶段就是漏了这条把机器压死的）。
12. 构造显存不足（连续加载多个模型）→ 得到可读的"请先卸载 XX"提示，界面不卡死，窗口不崩。
13. **崩溃恢复（用仅开发构建可用的调试入口验证，不是用户功能）**：注入一个已知在 DirectML 上不兼容的模型（如 BiRefNet）→ 推理失败要被捕获成可读提示，且推理子进程崩溃后主窗口存活、子进程被自动重启（D9 的直接验收）。
14. 对 RAW、GIF、超大分辨率图各跑一次 → 均落入 §6 表格中某一行的预期表现，无未捕获异常。

## 附录 A：实现细节（代码级，评审正文时可跳过）

> M0 已定案：引擎 = `onnxruntime-node` 的 DirectML 后端，推理跑 `utilityProcess` 子进程（D9/D11）。以下文件划分在实施计划里细化。

### A.1 新增主进程模块

| 文件 | 职责 | 依赖 |
|------|------|------|
| `electron/ai/capabilityCatalog.ts` | 纯数据：行为 → 候选模型 → 仓库/文件/体积/sha256/输入输出规格 | 无（可单测） |
| `electron/ai/modelStore.ts` | 下载、断点续传、sha256 校验、本地索引、删除回收 | fs、Node fetch |
| `electron/ai/inferenceChild.ts` | 运行于 `utilityProcess`：加载会话、执行推理、返回图像 buffer | `onnxruntime-node` |
| `electron/ai/aiService.ts` | 主进程侧：子进程生死、任务队列、超时/取消、派生文件落盘与元数据继承 | 上三者 + `xmpService` |

`electron/main.ts` 在 `app.whenReady` 内实例化 `AiService` 并注入 `registerIpc`，`will-quit` 时终止子进程（与现有 `scan?.dispose()` / `xmp?.dispose()` 同批，防孤儿进程）。

### A.2 新增 IPC 通道（沿用 `域:动作` + `IpcResult` 信封约定）

```
ai:catalog            → 行为 + 模型 + 各自本地状态（面板首屏一次拿全）
ai:model-download     → (modelId)
ai:model-cancel       → (modelId)
ai:model-delete       → (modelId)
ai:load / ai:unload   → (modelId)
ai:run                → (absPath, capability, modelId) → 单张
ai:run-batch          → 多张，M4 才注册
ai:discard            → (derivedPath)
ai:storage-stats      → 模型占用 + 可用磁盘 + 显存读数

事件（webContents.send）：
ai:download-progress / ai:load-progress / ai:run-progress / ai:state-changed
```

跨进程类型全部进 `shared/types.ts`（该文件不得 import electron），`electron/preload.ts` 白名单与 `src/api.ts` 三处严格同步——这是现有代码已有的约定，新增通道必须一次改齐三处。

### A.3 渲染层

- `src/store/useAiStore.ts`（zustand）与 `useAppStore` 并列，**不塞进 useAppStore**：预览层组件已 394 行，AI 状态独立分桶。
- `src/components/AiPanel.tsx` 挂载在 `PreviewOverlay` 内，由 `useAppStore.preview` 的存在与否控制可见。
- 订阅 `ai:*` 事件的模式与现有 `useThumbnails` / `onScanProgress` 一致（preload 的 `subscribe` 返回取消订阅函数）。

### A.4 下载器要点

- URL 基址用 `hf-mirror.com`（实测 200 可达；`huggingface.co` 直连超时）。
- Range 断点续传（实测镜像 CDN 支持 Range；本次实测持续下载 **1.27 MB/s**，历史另测到 4.09 MB/s，速率波动大，UI 进度不要按固定速率外推剩余时间）。
- 写 `*.part` → 完成后校验 sha256 → 改名就位。禁止直接写最终文件名。
- 不用 Windows 自带 `curl`（历史实测：下载 CDN 资源会因证书吊销列表不可达而 `CRYPT_E_REVOCATION_OFFLINE` 失败），用 Node `fetch`。

### A.5 打包与引擎裁剪（落实 D11 / D12）

- `package.json` 的 `build.files` 增加排除项，只保留 Windows x64 那一份原生库：
  `!node_modules/onnxruntime-node/bin/napi-v6/darwin/**`、`!node_modules/onnxruntime-node/bin/napi-v6/linux/**`、`!node_modules/onnxruntime-node/bin/napi-v6/win32/arm64/**`
- 这批 DLL 必须走 `asarUnpack`（与现有 exiftool 的 `app.asar.unpacked` 同一机制），否则运行时加载不到。
- 打包后校验：`dist/win-unpacked/resources/app.asar.unpacked` 里 `onnxruntime.dll + DirectML.dll + dxcompiler.dll + dxil.dll + onnxruntime_binding.node` 五个文件齐全，合计约 64 MB。
- **子进程创建会话时一律显式传 `intraOpNumThreads` / `interOpNumThreads`**（D12）。这是探针把开发机压到死机的直接原因，属硬性检查项，不允许依赖默认值。
