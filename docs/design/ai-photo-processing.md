## 1. 背景

PhotoTagManager 现在只做两件事：发现图片、把标签写进图片 XMP。用户在浏览到一张照片后，如果想对它做任何处理（抠图、修脸、变清晰），必须退出本应用、打开别的软件、处理完再导回来重新扫描。

本设计要在这个断点上接一段能力：**在预览界面里直接对当前照片发起一次 AI 处理，结果作为派生文件落回原目录，并自动带上标签。**

## 2. 目标与非目标

### 2.1 目标

| # | 目标 | 说明 |
|---|------|------|
| AG1 | 处理不出机器 | 全部推理在本机完成，照片内容不上传任何第三方服务 |
| AG2 | 代价先于效果可见 | 用户在点"下载"和"执行"之前，就知道这次要花多少磁盘、多少显存、大致多久 |
| AG3 | 原图永不被改 | AI 处理不产生任何不可逆操作，用户随时可删派生文件回到起点 |
| AG4 | 不破坏"文件是主数据" | 派生文件是普通图片文件，靠已有扫描机制被发现，不引入需要长期维护的中心数据库 |

### 2.2 非目标（本设计明确不做）

- **不做对话式 AI / 提示词生图**。本产品是图片管理器，"文生图""对话改图"会引入完全不同的交互范式和体量级得多的模型，另案。
- **不做实时预览**（拖动滑块→画面实时变化）。模型单次推理有秒级开销，实时性做不到，硬做只会得到一个卡顿的假象。所有处理都是"点执行 → 等一下 → 看结果"。
- **不做视频**。
- **不做模型训练/微调**，只做现成模型的下载与推理。
- **不做云端 API 兜底路线**（见 D5）。

## 3. 关键设计决策

| 编号 | 决策 | 理由与后果 |
|------|------|-----------|
| **D5** | **推理位置：纯本地** | 用户 2026-09-23 明确选定，放弃云端 API 路线。**后果**：必须自建模型下载与磁盘管理；8GB 显存构成硬上限，能同时驻留的模型数量受限；首次使用有几百 MB 到数百分钟的等待（取决于网速），必须把这等待做成可中断、可恢复、进度可见的。**代价**：放弃云端更强的效果与零下载的实现便利 |
| **D6** | **结果落地：同目录派生新文件** | 输出写到原图旁边 `原名.<action>.<ext>`，原图本体字节不变。**理由**：与本项目"标签跟文件"的迁移性一致——派生文件带着继承的标签，复制到别处仍然自描述；且完全可逆。**后果**：目录里会多出文件、占磁盘；派生文件会被下一次扫描发现并出现在网格中（这是期望行为，不另建"成果库"） |
| **D7** | **三层分离：行为 → 模型 → 运行时** | 用户看到的是"抠图""美颜"这种行为；行为下挂 1~3 个候选模型；模型底下才是真正的推理引擎。三层各自可独立增删。**理由**：模型生态换得快（今年好用的分割模型明年可能被替换），而"抠图"这个需求十年不变。把易变的部分压在中间层，UI 和 IPC 契约就不会随模型改动而震荡 |
| **D8** | **加载是显式动作，不是自动的** | 「已下载」与「已加载」是两个必须区分显示的状态。**理由**：8GB 显存下的压力不在权重（抠图 109 + 打标 181 + 人脸修复 325 ≈ **615 MB**，相对 8151 MiB 不算大），而在**推理期的激活张量与输入图占用**——这一项随输入分辨率变化，量级**尚未实测**，可能远大于权重本身。在没测出这个数之前，让系统自动同时驻留多个模型是无依据的冒险；一旦显存爆了，用户看到的是"点了没反应"，报错信息对他毫无意义 |
| **D9** | **推理跑在独立子进程，不在主进程** | 原生推理库是 C++ 代码，模型加载失败或显存溢出属于**进程级崩溃**。放主进程等于一张坏照片干掉整个应用窗口，用户会连带丢失正在进行的批量打标。**后果**：图像数据要跨进程传递，多一次序列化的开销（量级**尚未实测**）；需要子进程生死与重启管理 |
| **D10** | **派生文件继承原图标签 + 追加行为标签** | 抠图产出的文件自动带上原图的 `XMP-ptm:Tags`，再加一个行为标签（如 `AI抠图`）。**理由**：否则派生文件会脱离用户已有的标签体系，筛选时被孤立；行为标签则让"所有 AI 产物"可被一键筛出与批量清理 |

## 4. 功能设计

### 4.1 入口

预览界面（全屏大图）底部标签行的右侧，增加一个「AI 处理」按钮。点击后从右侧滑出面板，**悬浮在大图之上**，可拖拽边缘改变宽度，可随时关闭。

**为什么是抽屉而不是对话框**：现有预览界面已有顶栏（路径/翻页/定位/复制）与底栏（标签/信息），中部整块都是大图。弹窗会盖住正在处理的图，而"处理前/处理后"的对比是这项功能的核心体验——面板必须能收起，让位给大图本身。

**为什么不做在缩略图网格上**：网格是多选批量场景，而 AI 处理是单张、慢、有代价的操作。在网格里点十张跑十次抠图，会一次性占满显存队列。批量入口留到 M4，且必须先有队列与预估才开放。

### 4.2 面板内的工作流

```
选行为  →  选模型（带代价）  →  下载（如需）  →  加载（如需）  →  执行  →  看结果 → 保存 / 丢弃
   ↑                                                                          │
   └────────────────────────────── 换行为，重新走一遍 ←──────────────────────────┘
```

**第一屏是行为列表，不是模型列表。** 每行一个行为，右侧显示该行为下"当前默认模型"的名字与状态徽标。用户不关心 BiRefNet 还是 U²-Net，只关心"能不能把背景抠干净"。

**模型选择收在二级**：点开某个行为才展开它的候选模型。每个模型条目上必须直接显示四个代价字段——下载体积、落盘占用、显存需求（够不够）、单次耗时。其中体积是清单里的确定数字（见 4.3），显存与耗时在 M0 探针前一律显示为「未测定」，**不允许编一个数糊上去**。

**状态徽标**（同一时刻每个模型只有一个状态）：

| 状态 | 可用操作 |
|------|---------|
| 未下载 | 下载 |
| 下载中 | 取消（进度可见，支持断点续传） |
| 已下载·未加载 | 加载 / 删除（回收磁盘） |
| 已加载·空闲 | 执行 / 卸载（释放显存） |
| 推理中 | 取消 |
| 不可用 | 无操作，显示原因（磁盘不足 / 无可用加速设备 / 校验失败） |

### 4.3 首版行为与模型清单

清单里的模型、体积、文件路径均来自 2026-09-23 对 `hf-mirror.com` API 的实际查询（命令见附录 B），非推测。

| 行为 | 面向用户的说法 | 候选模型 | 下载体积 | 阶段 |
|------|--------------|---------|---------|------|
| 抠图 | 去除背景 | BiRefNet-lite（fp16） | 109 MB | M1 |
| 抠图 | 去除背景 | BiRefNet-lite（fp32，质量档） | 214 MB | M1 可选 |
| 智能打标 | 自动建议标签 | CLIP ViT-B/32（q4） | 181 MB | M1 |
| 美颜 | 磨皮 / 五官微调 | 待选 | — | M3，**模型源未定** |
| 人脸修复 | 老照片 / 低清人脸清晰化 | GFPGANv1.4（onnx） | 325 MB | M3 |
| 深度图 | 背景虚化 / 景深 | Depth Anything V2 small（int8） | 26 MB | M3 可选 |
| 超分 | 放大变清晰 | — | — | **不进清单**，见下 |
| 可编辑抠图 | 手动补选区域 | SAM ViT-B（quantized） | 101 MB | M4 |

**为什么超分不进首版**：探测发现镜像上名为 `Real-ESRGAN-ONNX` 的社区仓库，其 `model.onnx` 实际大小是 **0.0 MB**——那是未解析的 Git LFS 指针文件，不是模型。写进清单就会出现一条"永远下不动"的条目，且下载器会把它当成一个几十字节的成功文件。**结论：可信源没找到之前，超分不承诺。** 这条要落进 M0 探针的待办里。

**为什么 M1 选抠图 + 智能打标，而不是原话里的美化/美颜**：

- 打标能复用已经跑通并测过的 `tags:write-image` 链路，不产生新存储，是"改动面最小、和业务本体最贴"的一条。本产品的核心资产就是标签，AI 直接喂标签体系才算长在主干上。
- 抠图是"要产生派生文件"这一类里最简单的一个：单模型、单输入单输出、无前置检测。
- 美颜是两段式流水线（先人脸检测定位，再对人脸区域修复），拿它当第一个行为，会把"链路通不通"和"效果好不好"两件事混在一起测，失败时分不清是下载、加载、推理还是落盘的问题。

### 4.4 派生文件的命名与内容

| 行为 | 输出文件名 | 容器格式 | 为什么 |
|------|-----------|---------|--------|
| 抠图 | `原名.cutout.png` | PNG | 必须带 alpha 通道，JPEG 会丢透明度 |
| 美颜 | `原名.beauty.jpg` | JPEG | 质量参数默认值**待 M3 实施时定**，不预设 |
| 人脸修复 | `原名.restore.jpg` | JPEG | 同上 |
| 智能打标 | **不产生新文件** | — | 直接写原图 XMP |

派生文件写入元数据：继承原图全部 `XMP-ptm:Tags` + 追加行为标签 + 保留拍摄时间等原始 EXIF（用现有 exiftool 通道复制，不重新编码元数据）。

**同名冲突**：`原名.cutout.png` 已存在时不覆盖，改用 `原名.cutout.2.png`，并在界面上说明为什么多了一个序号——用户必须能预期文件名怎么来的。

### 4.5 结果查看与撤销

执行完成后，面板内显示"处理前 / 处理后"双栏对比，并提供三个动作：

- **保存**：派生文件正式留在目录里（实际上文件已写盘，"保存"是指停止"待确认"态并提示可去资源管理器查看）
- **丢弃**：删除刚生成的派生文件，目录回到处理前
- **替换原图**：**不提供**。要用户自己去资源管理器操作，本应用不做不可逆动作（AG3）

## 5. 磁盘与显存管理

### 5.1 磁盘

- 模型文件存放于应用数据目录下的独立子目录，与原图目录完全分离，不与缩略图缓存混放。
- 面板顶部常驻一行「模型占用 X GB · 可用磁盘 Y GB」。C 盘当前剩 247 GB（实测），但用户可能在别的盘，需运行时读取。
- 下载前预估：`(模型体积) > (可用磁盘 - 安全余量)` 时直接拒绝并说明，不允许下到一半写满磁盘。**安全余量取值未定**——拍一个数是假指标，M0 实测写入速度时一并定。
- 删除模型必须同时清掉临时文件与索引记录，不留孤儿。

### 5.2 显存与并发

- 同一时刻**只允许一个推理任务在跑**，其余排队。首版不做并发调度，8GB 显存下并发是负收益。
- 面板显示「已用显存 / 总量」（当前实测总量 8151 MiB）。
- 加载新模型导致显存不足时：明确报"显存不足，请先卸载 XX"并给一键卸载，不静默换 CPU 跑（换 CPU 会从秒级掉到几十秒级，用户会以为卡死——但**CPU 具体耗时未实测**，实测后可考虑提供"改用 CPU"的显式选项）。
- 空闲卸载：加载后连续空闲一段时间自动卸载。**时长未定**，等 M0 实测单次加载耗时后按"加载代价 / 复用上界"算，不拍脑袋。

## 6. 失败与边界

| 场景 | 表现 | 为什么这样 |
|------|------|-----------|
| 下载中断 | 保留 `.part` 断点，重开可续传 | 数百 MB 在实测 4 MB/s 量级下要几十秒到数分钟，重头下不可接受 |
| 校验失败（sha256 不符） | 删除文件、报"下载内容损坏，请重试" | 静默用坏文件会在推理阶段崩得莫名其妙 |
| 子进程崩溃 | 主进程感知并重启子进程，当前任务标失败并提示重试 | 用户不能因为一张坏图丢窗口（D9 的全部理由） |
| 显存不足 | 见 5.2 | |
| 原图过大（超模型输入上限） | 处理前按模型规格自动降采样，并在界面注明"已在 NxN 下处理" | 不降采样会直接崩；不注明则用户以为是模型效果差 |
| RAW / HEIC 输入 | 先转码为模型可吃的格式再处理，转码中间文件用完即删 | 现有代码已记录 RAW/HEIC 写 XMP 可能不被 exiftool 支持，输入侧同样要防 |
| GIF / 多帧图 | 明确拒绝，只处理首帧或提示不支持 | 抠图多帧 GIF 的产物形态没有共识，别猜 |
| 磁盘写满 | 中止、回滚已写的派生文件、报剩余空间 | |
| 无可用 GPU 加速设备 | 清单里所有条目转「不可用」并说明原因，允许显式选择 CPU 慢速模式 | 不能让用户面对一片没有任何解释的灰按钮 |

## 7. 分期实施

| 阶段 | 内容 | 完成判据 |
|------|------|---------|
| **M0 探针**（不进仓库） | 临时目录里用 BiRefNet-lite fp16 真跑一次；同时验证 DirectML / CUDA / WebGPU / CPU 四条路在本机 RTX 5060（Blackwell sm_120）上哪条能加载；记录耗时、峰值显存、峰值内存；顺带找超分的可信源 | 输出一份"哪个 EP 能跑 + 真实耗时显存数字"，用它替换掉本文件里所有「未实测」占位 |
| **M1 链路打通** | 抠图 + 智能打标两个行为；清单 / 下载 / 加载 / 推理 / 派生文件 / 写 XMP / 丢弃 全流程 | 见 §8 |
| **M2 界面与恢复** | 面板可拖宽、状态持久化（重启后模型不必重下重加载提示）、失败重试交互 | 冷启动后已下载模型显示为"已下载·未加载"，不重复下载 |
| **M3 效果类行为** | 美颜（两段式人脸流水线）、人脸修复、深度图 | 每个行为有独立的处理质量说明与已知局限 |
| **M4 批量** | 整目录批量、队列可视化、失败清单与单独重试 | 批量 100 张不阻塞界面操作，中断可续 |

M0 是后续所有阶段的前置：没有它，本文件里的耗时、显存、余量三处都是空的，写进实现计划会变成假指标。

## 8. M1 验收

以下每条都要在真实构建产物上手动走一遍，不看单测绿灯当交付（M0 探针与 typecheck/test 是证据的一部分，不覆盖行为正确性）：

1. 全新环境（`userData` 下模型目录为空）打开面板 → 抠图显示「未下载」，体积显示 109 MB。
2. 点下载 → 进度条推进 → 中断应用重启 → 再次下载从断点继续，不从头开始。
3. 下载完成 → 状态变「已下载·未加载」→ 磁盘上文件 sha256 与清单一致。
4. 点加载 → 状态变「已加载·空闲」→ 显存读数上升，且上升量与 M0 实测值同量级。
5. 点执行 → 有明确的处理中指示 → 完成后同目录出现 `原名.cutout.png`，**原图字节未变**（比对 mtime 与 sha256）。
6. 派生文件透明区域正确：放进预览界面切到深色背景可见抠图结果边缘，不是黑底。
7. 派生文件带原图全部标签 + `AI抠图` 标签；重新扫描后它能被 `AI抠图` 筛出。
8. 点丢弃 → 派生文件消失，目录回到处理前状态。
9. 智能打标 → 不产生新文件，标签直接出现在原图标签行；再次执行不产生重复标签。
10. 拔掉 GPU（强制 CPU 模式）→ 界面明确说明当前走 CPU 及其代价，而不是无声变慢。
11. 构造显存不足（连续加载多个最大档模型）→ 得到可读的"请先卸载 XX"提示，界面不卡死，窗口不崩。
12. 对 RAW、GIF、超大分辨率图各跑一次 → 均落入 §6 表格中某一行的预期表现，无未捕获异常。

### A.1 新增主进程模块

| 文件 | 职责 | 依赖 |

| `electron/ai/capabilityCatalog.ts` | 纯数据：行为 → 候选模型 → 仓库/文件/体积/sha256/输入输出规格 | 无（可单测） |
| `electron/ai/modelStore.ts` | 下载、断点续传、sha256 校验、本地索引、删除回收 | fs、Node fetch |
| `electron/ai/inferenceChild.ts` | 运行于 `utilityProcess`：加载会话、执行推理、返回图像 buffer | `onnxruntime-node` |
| `electron/ai/aiService.ts` | 主进程侧：子进程生死、任务队列、超时/取消、派生文件落盘与元数据继承 | 上三者 + `xmpService` |

`electron/main.ts` 在 `app.whenReady` 内实例化 `AiService` 并注入 `registerIpc`，`will-quit` 时终止子进程（与现有 `scan?.dispose()` / `xmp?.dispose()` 同批，防孤儿进程）。

### A.2 新增 IPC 通道（沿用 `域:动作` + `IpcResult` 信封约定）

```
ai:catalog            → 行为 + 模型 + 各自本地状态（面板首屏一次拿全）
ai:model-download     → (modelId)
ai:model-cancel       → (modelId)
ai:model-delete       → (modelId)
ai:load / ai:unload   → (modelId)
ai:run                → (absPath, capability, modelId) → 单张
ai:run-batch          → 多张，M4 才注册
ai:discard            → (derivedPath)
ai:storage-stats      → 模型占用 + 可用磁盘 + 显存读数

事件（webContents.send）：
ai:download-progress / ai:load-progress / ai:run-progress / ai:state-changed
```

跨进程类型全部进 `shared/types.ts`（该文件不得 import electron），`electron/preload.ts` 白名单与 `src/api.ts` 三处严格同步——这是现有代码已有的约定，新增通道必须一次改齐三处。

### A.3 渲染层

- `src/store/useAiStore.ts`（zustand）与 `useAppStore` 并列，**不塞进 useAppStore**：预览层组件已 394 行，AI 状态独立分桶。
- `src/components/AiPanel.tsx` 挂载在 `PreviewOverlay` 内，由 `useAppStore.preview` 的存在与否控制可见。
- 订阅 `ai:*` 事件的模式与现有 `useThumbnails` / `onScanProgress` 一致（preload 的 `subscribe` 返回取消订阅函数）。

### A.4 下载器要点

- URL 基址用 `hf-mirror.com`（实测 200 可达；`huggingface.co` 直连超时）。
- Range 断点续传（实测镜像 CDN 支持 Range，历史持续下载 4.09 MB/s 量级）。
- 写 `*.part` → 完成后校验 sha256 → 改名就位。禁止直接写最终文件名。
- 不用 Windows 自带 `curl`（历史实测：下载 CDN 资源会因证书吊销列表不可达而 `CRYPT_E_REVOCATION_OFFLINE` 失败），用 Node `fetch`。
