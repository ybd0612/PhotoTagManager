## 1. 背景

PhotoTagManager 现在只做两件事：发现图片、把标签写进图片 XMP。用户在浏览到一张照片后，如果想对它做任何处理（抠图、修脸、变清晰），必须退出本应用、打开别的软件、处理完再导回来重新扫描。

本设计要在这个断点上接一段能力：**在预览界面里直接对当前照片发起一次 AI 处理，结果作为派生文件落回原目录，并自动带上标签。**

## 2. 目标与非目标

### 2.1 目标

| # | 目标 | 说明 |
|---|------|------|
| AG1 | 处理不出机器 | 全部推理在本机完成，照片内容不上传任何第三方服务。**这条必须可验证**：处理期间除模型下载外不得有任何出站网络请求（验收 §8 有对应项），不能只当口号 |
| AG2 | 代价先于效果可见 | D14 之后没有独立的"点下载"动作，所以代价告知发生在**点击行为按钮的那一刻**：一次性说明"要下载多少、占多少磁盘、大致多久"，确认后才动手 |
| AG3 | 原图永不被改 | AI 处理不产生任何不可逆操作。D18 之后这条更强：**用户不点保存，照片目录里连一个字节都不会多**（结果只存在于暂存） |
| AG4 | 不破坏"文件是主数据" | 派生文件是普通图片文件，靠已有扫描机制被发现，不引入需要长期维护的中心数据库 |

### 2.2 非目标（本设计明确不做）

- **不做对话式 AI / 提示词生图**。本产品是图片管理器，"文生图""对话改图"会引入完全不同的交互范式和体量级得多的模型，另案。
- **不做"拖动滑块即时刻画"式的实时预览**。注意这与 D18 的**「预览后落盘」是两件事**，别混为一谈：后者是"先把整张算完 → 再预览 → 再决定留不留"，前者是"边拖边重算"。前者代价不可控（同图被反复推理几十次），仍不做。
  - 但 D18 的暂存缓存带来一个副产品：**同一张图 + 同一模型再次处理时命中缓存，可以秒出预览**，不需要重跑。这不是实时预览，是缓存命中。
- **不做视频**。
- **不做模型训练/微调**，只做现成模型的下载与推理。
- **不做云端 API 兜底路线**（见 D5）。

## 3. 关键设计决策

| 编号 | 决策 | 理由与后果 |
|------|------|-----------|
| **D5** | **推理位置：纯本地** | 用户 2026-09-23 明确选定，放弃云端 API 路线。**后果**：必须自建模型下载与磁盘管理；8GB 显存构成硬上限；首次使用要等下载——实测 hf-mirror 下载速率 **1.27 MB/s**（213.6MB 用 168.8s）到 **0.39 MB/s**（4.36MB 用 11.3s，小文件受握手开销拖累），即一个 100MB 模型约需 1~4 分钟，必须做成可中断、可续传、进度可见的。**代价**：放弃云端更强的效果与零下载的实现便利 |
| **D6** | **结果落地：同目录派生新文件，保存时才落盘** | 输出最终写到原图旁边 `原名.<action>.<ext>`，原图本体字节不变。**理由**：与本项目"标签跟文件"的迁移性一致——派生文件带着继承的标签，复制到别处仍然自描述；且完全可逆。**落盘时机是"用户点保存之后"**（见 D18），处理结果先待在预览暂存里。**后果**：目录里会多出文件、占磁盘；派生文件会被下一次扫描发现并出现在网格中（这是期望行为，不另建"成果库"） |
| **D7** | **三层分离：行为 → 模型 → 运行时** | 用户看到的是"抠图""美颜"这种行为；行为下挂 1~3 个候选模型；模型底下才是真正的推理引擎。三层各自可独立增删。**理由**：模型生态换得快（今年好用的分割模型明年可能被替换），而"抠图"这个需求十年不变。把易变的部分压在中间层，UI 和 IPC 契约就不会随模型改动而震荡。<br>**用户 2026-09-23 明确要求"代码通用点，后面可拓展其他模型"，具体化为三条可验收约束**：① 新增一个模型 = 只往清单加一条数据，**不改** UI 组件、不改 IPC 通道；② 新增一个行为 = 只加清单条目 + 一个后处理函数，底栏按钮与下拉自动多一项；③ 推理子进程按「输入张量规格 + 输出后处理函数」抽象，**不允许**把 `320×320`、`sigmoid`、`u2netp` 这类具体形状写进通用代码路径。违反其中任何一条就是三层分离被击穿，评审时要专门看。 |
| **D8** | **加载的代价是秒级，因此降级为内部状态** | M0 实测：u2netp（4.4MB）加载 **0.96s**、推理 **21ms**（DirectML）；换到 213MB 的模型加载 **3.14s**。这个量级不足以让用户单独做一次"加载"动作，所以 v0.1 里「已下载·未加载 / 已加载·空闲」两个用户可见状态在 D14 中合并为「已就绪」，加载在点行为时静默完成。<br>**显存**：一次 u2netp 推理使整卡显存从 853 → 1178 MiB（**Δ325 MiB**，口径是整卡 `nvidia-smi memory.used`，含其他进程，非本应用独占）。相对 8151 MiB 总量，同时驻留 3~4 个这类模型在数字上是宽松的，但大模型的激活占用随输入分辨率涨，**仍按"一次只驻留一个"设计**，等 §4.3 清单逐个测过再考虑放宽 |
| **D9** | **推理跑在独立子进程，不在主进程** | 原生推理库是 C++ 代码，失败方式是**进程级崩溃**。**这条已被实测证实不是理论担忧**：BiRefNet-lite 在 DirectML 上加载成功，但一执行就抛 `DmlFusedNode_19_64` 原生错误（ONNX Runtime 的 `sequential_executor.cc` 直接返回非零状态）。这类错误发生在主进程就等于一张坏照片干掉整个窗口，用户连带丢失正在进行的批量打标。**后果**：图像数据要跨进程传递，多一次序列化开销（未实测，但相对 21ms 的推理时间可忽略）；需要子进程生死与重启管理 |
| **D10** | **派生文件继承原图标签 + 追加行为标签** | 抠图产出的文件自动带上原图的 `XMP-ptm:Tags`，再加一个行为标签（M1 为 `AI人像抠图`）。**理由**：否则派生文件会脱离用户已有的标签体系，筛选时被孤立；行为标签则让"所有 AI 产物"可被一键筛出与批量清理。<br>**约束**：行为标签名是**清单里的一个字段**（单一事实源），UI、写入、筛选项都从清单取，**禁止在代码里各处硬编码字符串**。v0.5 文档内就曾同时出现 `AI抠图` 与 `AI人像抠图` 两种写法——那种不一致到了代码里就是筛选漏一半的 bug |
| **D11** | **引擎 = `onnxruntime-node` 的 DirectML 后端；不做插件，随包分发** | M0 实测：DirectML 在本机 RTX 5060（Blackwell）上可用；同一模型同一输入连跑三次 CPU 约 201ms、DirectML 为 20/8/7ms，**约快 10~29 倍**（区间是波动，不取单点）。CUDA 后端在 npm 预编译包里**根本不存在**（`backend not found`）；`ort-web` 的 WebGPU 后端在 Electron 31 里**会话创建死锁**（连 4.4MB 模型 180s 不返回；注意 WebGPU 本身可用，死的是 ort-web 这层）。<br>**推翻 v0.1 的体积估算**：v0.1 按 npm 报的 `unpackedSize=301MB` 推出"安装包翻倍、所以必须做插件"，这条链是错的——287MB 落盘里含 darwin/arm64 85MB、win32/arm64 69MB、linux 两平台 92MB，本项目只发 Windows x64。**真正要带的只有 `bin/napi-v6/win32/x64` = 64.0 MB**（onnxruntime.dll 27.4 + DirectML 17.7 + dxcompiler 17.2 + dxil 1.4 + 绑定 0.3）。安装包 89.8 → 约 115 MB，安装后 352 → 约 416 MB（+18%）。**为 18% 引入插件机制（双安装包发版矩阵、杀软对运行时落地 DLL 的误报、引擎版本与 Electron 升级绑死）不划算**，故随包分发 + 打包时裁掉其他平台目录 |
| **D12** | **CPU 后端必须显式限制线程数** | 实测事故：213MB 模型走 CPU 后端且未设 `intraOpNumThreads` 时，ONNX Runtime 默认占满本机 32 个逻辑核，10 分钟不结束、单进程吃 **6.3GB** 内存，**把开发机压到无响应**。因此任何 CPU 兜底路径都要显式限核（默认建议 2~4，实施时定），并在界面上明确标出"当前走 CPU，会慢很多"，不允许无声降级。<br>**M1 实现口径（v0.7 定）**：限核取 **2**（实测并行度 1.99 核）；开关放在**组合按钮的下拉底部**（不放设置页——那里 M1 的参数区必须为空，且设置页不许出现任何控件的判据会因此变模糊），勾选后**底栏常驻**一句代价说明；**后端变化必须重建推理会话**，否则第二次点击会复用旧后端的会话，形成反向的无声降级；该选择**不持久化**，重启回 GPU |
| **D13** | **入口 = 预览底栏的组合按钮「抠图 ▾」** | 主按钮 + 右侧模型下拉。**取消** v0.2 的"AI 处理抽屉 + 行为列表"两层结构。**理由**：用户心里想的是"抠图"，不是"打开 AI 再挑一个"，中间那层是白多一次点击；而换模型是低频但强场景绑定的操作，不该把人赶到设置页。**主按钮语义恒定**：永远只表示"用当前模型处理这张图"，不随内部状态换含义。**后果**：行为数量会涨（M3 预计 5 个），所以溢出策略（横向滚动 + 超 5 个收进「更多」）必须现在定，不能等加行为时改布局 |
| **D14** | **首次使用：一次点击走完 下载→加载→推理** | 下载与加载**不再是用户可见的独立动作**。**理由**：实测模型只有 4.4MB、约 4~11 秒，加载 0.96 秒——为这么点代价设计"点下载→等→点加载→等→点抠图"的三段式，等于把内部状态搬到人面前当操作步骤，用户要为一次 21 毫秒的计算点三下。**唯一保留的询问**是首次下载前那一句（要联网、要占磁盘，符合 AG2）；加载不询问。**代价**：进度、取消、断点续传的能力都在，只是收进一次点击内部；想手动控制的人去下拉（D17）。AG2 由"下载前显示代价"变成"点击时提示一句要下多少" |
| **D15** | **对比默认「按住看原图、松开看结果」，底纹为棋盘格** | 左右分屏降为可切换的次要模式。**两个理由**：① 按住模式对齐精确、直接看边缘质量；② 分屏对抠图天生不利——掩码在 320×320 算出后放大回原尺寸，右图必然比左图糊，用户第一眼会误判成程序坏了。<br>**底纹是硬性要求，样式定为棋盘格**（用户 2026-09-23 选定）：透明区若直接铺窗口会被渲染成白/黑底，无法区分"抠干净"与"渲染错"（探针里就是这么差点被骗过去，改压品红底才看清） |
| **D16** | **新建应用级「设置」总入口，但它只管参数与只读统计** | 当前应用没有任何全局偏好入口（只有「关于」「标签管理」两个弹窗），AI 需要一个能长期生长的地方，所以补总入口而不是做 AI 专属弹窗。**但模型管理不进设置页**（见 D17）。<br>**要说清参数是什么**：U²-Netp 这类模型本身几乎无可调项，能调的是掩码阈值、腐蚀尺寸、形态学清理、去色边这类**后处理**参数（已查证的候选集见 §4.7 的 rembg `remove()` 表）。把它写成"模型参数"会做出一个空壳设置页。M1 只要求骨架存在、参数区可为空、**禁止调了没反应的假控件** |
| **D17** | **模型管理的唯一入口 = 组合按钮的下拉；同一状态只允许一处可改** | 下拉里列出候选模型，显示体积 / 是否已下载 / 是否已加载，并提供 `[下载]` `[卸载]` `[删除]` `[设为默认]`。设置页**不重复**提供这些操作。<br>**理由**：同一份状态出现在两处 UI，改一处忘一处，早晚不一致；而且换模型是"就在眼前要用"的操作，不该让人去别处。<br>**两条附带的 UI 约束**：① **hover 只显示状态、不承载动作**——悬停出来的入口对键盘和触屏用户不可达，动作必须能点、能 Tab 到；② **进行中不得置灰**——灰色等于"禁用/坏了"，用户会以为程序出问题。进行中用按钮背景填充进度 + 文字保持可读对比 + 给「取消」 |
| **D18** | **预览后落盘：结果先进暂存，保存才进照片目录** | 用户 2026-09-23 提出。**流程**：处理完成 → 写暂存 → 预览对比 → 保存（移入原图目录）或不保存（留在暂存待清理）。<br>**它顺手解决的真问题**：v0.4 §4.6 那个"异常退出会在用户目录留下垃圾、需要启动时提示处置"的补丁**整段作废**——文件从没进过用户目录，就没有污染用户目录这回事。<br>**命名警告**：这不叫"实时预览"（§2.2 已明确否掉拖滑块实时重算）。叫**预览后落盘**。写错名字会误导实施的人去做防抖。<br>**三条硬约束**：<br>① **暂存目录必须在 `userData` 下，绝不能在照片目录里。** 现有扫描器只按扩展名过滤图片（`shared/imageExt.ts`），它不认识"temp"这个概念——放照片目录里的半成品会被直接扫进用户网格。<br>② **缓存内容 = 成品图**（用户选定）。**直接推论：参数必须进缓存键**——成品图是"模型 + 参数"的函数，键里不含参数就会出现"用户把阈值从 240 调到 200，拿到的还是 240 那张旧图，界面却当成新结果展示"这种**看起来对、实际错、且无任何报错**的 bug。<br>代价如实记下：改参数即未命中、要重跑。当前 u2netp 推理仅 21ms，这个代价可忽略；**但将来上 GFPGAN / CLIP 这类慢模型时这条要重新评估**（改成缓存掩码可把后处理与推理解耦，实测掩码 29KB 对成品 1119KB，小 38 倍）。<br>③ **缓存键 = 五元组**，缺一项就有一类失效：<br>`sha1( 原图指纹 : 模型指纹 : 输入尺寸 : 后处理参数 : 预处理管线版本 )`<br>· 原图指纹**照抄现有缩略图约定** `sha1(absPath : mtimeMs : size)`，别另造一套 → 漏了会拿旧结果当新图<br>· 模型指纹 = 权重文件 sha256 → 漏了会在重新下载/换源后复用旧结果<br>· 后处理参数 → 见 ②<br>· **预处理管线版本** = 我们自己那套解码/EXIF 转正/转码/resize 的代码版本，是一个手工递增的常量 → **漏了最隐蔽**：换了转码器或改了 resize 算法，缓存里全是旧管线烘出来的图，还都对得上键<br>**清理**：保留期可设（默认建议 30 天）**且**有总量上限，超上限按最久未用淘汰。只按时间清理等于假设用户用量恒定。 |

## 4. 功能设计

### 4.1 入口

预览界面（全屏大图）底栏，**每个行为是一个组合按钮**：主按钮 + 右侧一个小下拉。M1 就一个 `「抠图 ▾」`，后续每实测通过一个行为就多一个。

- **主按钮永远只表示一件事**：用当前模型处理这张图。它不表示"下载"、不表示"加载"，也不随内部状态换含义。
- **下拉是模型管理的唯一入口**：列出该行为下的候选模型，每行显示**名称 · 体积 · 状态标签**，右侧一个主动作按钮（未下载→`[下载]`、已加载→`[卸载]`、已下载未加载→`[删除]`，**一行只给一个**）。**整行就是选项**：点行、回车、空格都表示"用这个模型"，不设独立的"默认"控件（09-30 第二版：先做成复选框，用户反馈复选框是多余的一层，点整行才是他要的语义）。想细看和控制的人在这里操作，不想管的人一次点击主按钮就走完。
- **选中态必须与"键盘焦点行"分成两档**：选中行给主色底 + 左侧 3px 主色条 + 模型名转主色加粗；键盘焦点行只给浅灰。两档原来共用 `action.selected`，结果是"哪行是当前模型"根本读不出来。
- **撤掉可见控件不等于撤掉语义**：行的 role 用 `menuitemradio` + `aria-checked`，读屏软件仍能说出哪行被选中；行内那颗动作按钮必须 `stopPropagation`，否则点「卸载」会顺手把默认模型换掉。

**为什么用组合按钮而不是"一个按钮 + 设置页选模型"**：换模型是低频但强场景绑定的操作——人是在准备抠这张图时才想到"要不要换个模型试试"。把它放到设置页等于让用户离开现场去改一个马上要用的东西。

**三条必须遵守的实现约束**：

1. **hover 只显示状态，不承载动作**。下载/卸载/删除必须能通过点击到达，键盘 Tab 能走到下拉里每一项——悬停出来的入口对键盘和触屏用户是不可达的，也与现有代码的无障碍标注习惯冲突。
2. **进行中不得置灰**。灰色在 UI 语言里等于"禁用/坏了"，用户看到灰底会以为程序出问题，而不是"正在下载"。进行中用**按钮背景从左往右填充进度**，文字保持可读对比，旁边给「取消」。
3. **驻留状态是快照，每次处理结束必须重取**。`loaded` 来自主进程 `runner.loadedModelId`，渲染层拿的是拉清单那一刻的快照。成功事件不刷清单，跑完这一次界面上就仍然写着"已下载"——用户看不出谁在内存里，也找不到那颗「卸载」（2026-09-30 CDP 实测抓到，两行都停在"已下载"）。失败事件早就在刷，同一处理成功路径也要刷；缓存命中同样要刷（那时驻留可能已被用户点卸载改掉）。

**按钮溢出策略（现在就定，避免加行为时改布局）**：底栏按钮区可横向滚动；超过 5 个时后面的收进一个「更多」下拉。M1 只有一个，但布局按可扩展做，不允许写成"只有一个所以不管溢出"。

**为什么不做在缩略图网格上**：网格是多选批量场景。推理本身很快（实测 21ms），所以瓶颈不在算力，而在**产物**——批量跑 100 张就是 100 个新文件占磁盘，而抠图这类结果必须人逐张看一眼才知道对不对，成批产出错误结果等于成批垃圾文件。批量入口留到 M4，且必须先有队列、失败清单与磁盘预估才开放。

### 4.2 点一下主按钮之后发生什么

```
点「抠图」
   ├─ 模型已就绪 ─────────────────────────────┐
   ├─ 未下载 → 弹一句"首次使用需下载 4.4MB，约 10 秒"
   │            用户确认 → 下载 →（自动）加载 ──┤→ 抠图 → 写暂存 → 对比视图 → 保存 / 不保存
   └─ 已下载未加载 → 静默加载（约 1 秒）────────┘
```

结果一律**先写暂存**（`userData` 下），"保存"才移入照片目录，"不保存"就是什么都不做（D18）。

**一次点击走完整个流程。** 用户点主按钮，若模型未就绪，应用把 下载 → 加载 → 推理 串成一次操作，中间**不要求第二次点击**。三段进度都反映在同一个按钮的背景填充上（不置灰，见 §4.1），随时可取消。

**唯一的例外是首次下载要问一句**：因为这是本功能第一次联网、第一次占磁盘。实测速率 0.39~1.27 MB/s，4.4MB 约 4~11 秒，提示里给体积和大致耗时（AG2）。加载不弹提示——实测 0.96 秒，弹一次询问的打扰大于收益。

**"加载"对用户不是步骤，但仍是内部状态**：下拉里如实显示，供想管的人看。

**内部状态与用户所见**：

| 内部状态 | 主按钮显示 | 下拉里可做 |
|------|---------|---------|
| 未下载 | 「人像抠图」可点 | 下载 |
| 就绪流程中（下载·加载·推理） | 背景进度 + 「取消」，**不置灰** | 取消 |
| 已下载未加载 | 「人像抠图」可点，点即出结果 | 删除 |
| 已加载 | 「人像抠图」可点，点即出结果 | 卸载（卸完该行即给出删除） |
| 不可用 | 「人像抠图」可点，点后明确说明原因 | 无 |

`[默认]` 复选框不随上表变化：只要模型可用就能勾，勾中即成为该行为的默认模型（单选，不存在"无默认"）。

**「该模型在本引擎不支持」是真实存在的状态**，不是理论：M0 实测 BiRefNet 在 DirectML 上加载成功但一执行就崩。所以清单里每个模型都要带"是否已实测跑通"的标记（见 §4.3）。

### 4.3 行为与模型清单（含 DirectML 实测状态）

体积与路径来自 2026-09-23 对 `hf-mirror.com` API 的实际查询；"DirectML 实测"列来自同日在真机上的加载与推理验证（命令见附录 B）。

| 通用抠图 | 去除任意主体背景 | BiRefNet-lite（fp32） | 214 MB | ❌ **加载成功 3.14s，推理报 `DmlFusedNode` 原生错误** | M3，需换模型（Q14） |
| 通用抠图 | 同上 | BiRefNet-lite（fp16） | 109 MB | ⛔ 未测。且 fp16 路径在本环境另有风险 | M3，待测 |

**新增硬规则：只有「已跑通」的条目才能出现在用户界面里。** M0 的教训是——同一个引擎上 u2netp 跑得漂亮、BiRefNet 一执行就崩。"仓库里有这个文件"和"这个功能可用"之间没有任何必然联系，清单不能靠查 API 体积来成立。

**为什么 M1 首个行为叫「人像抠图」而不是「抠图」**：U²-Netp 是人像 matting 模型。探针拿一张演唱会现场照测，它把舞台亮部当成了主体（前景占比 8.7%，轮廓连贯但完全选错对象）。链路与性能都是真的，**通用性不是**。所以 M1 对用户就写"人像抠图"，通用抠图留到 Q14 测出可用的模型再开。

**为什么超分不进清单**：镜像上名为 `Real-ESRGAN-ONNX` 的社区仓库，其 `model.onnx` 实际大小是 **0.0 MB**——那是未解析的 Git LFS 指针文件。写进清单就会出现一条"永远下不动"的条目，且下载器会把它当成一个几十字节的成功文件。**可信源找到之前，超分不承诺。**

**为什么 M1 只带「人像抠图」这一个行为**：

- 它是目前**唯一在 DirectML 上真跑通、有实测耗时和真实产物**的一条。M1 的任务是把骨架（清单 / 下载续传 / 加载 / 派生文件 / 标签继承 / 丢弃 / 崩溃恢复）做完做稳，骨架不该和"某个模型到底能不能用"绑在一起验证。
- 智能打标虽然和业务本体最贴（能直接复用已经跑通并测过的 `tags:write-image` 链路，零新存储），但 **CLIP 从未在本环境跑过**（Q15）。它值得做，但要带着实测记录进 M3。
- 美颜是两段式流水线（先人脸检测定位，再对人脸区域修复），拿它当第一个行为会把"链路通不通"和"效果好不好"混在一起测，失败时分不清是下载、加载、推理还是落盘的问题。

### 4.4 派生文件的命名与内容

| 行为 | 输出文件名 | 容器格式 | 为什么 |
|------|-----------|---------|--------|
| 人像抠图 | `原名.cutout.png` | PNG | 必须带 alpha 通道，JPEG 会丢透明度 |
| 美颜 | `原名.beauty.jpg` | JPEG | 质量参数默认值**待 M3 实施时定**，不预设 |
| 人脸修复 | `原名.restore.jpg` | JPEG | 同上 |
| 智能打标 | **不产生新文件** | — | 直接写原图 XMP |

派生文件写入元数据：继承原图全部 `XMP-ptm:Tags` + 追加行为标签 + 保留拍摄时间等原始 EXIF（用现有 exiftool 通道复制，不重新编码元数据）。

**两个必须处理、否则产物就是错的细节：**

- **EXIF Orientation（旋转标记）**。手机照片的像素常常是横的，靠方向标记告诉查看器"显示时转 90°"。模型吃的是**像素**，不吃这个标记。所以必须明确一条规则：**解码时统一按 EXIF 转正，模型输入、掩码、输出全用转正后的方向**，输出 PNG 不再写方向标记。搞错的后果是抠出来的图相对原图旋转了 90°——而 M0 探针那张测试图恰好没有方向标记，**所以"跑通"并没有覆盖这个场景**。
- **ICC 色彩配置**。宽色域照片（如 Display P3）若重编码时丢掉 ICC 剖面，颜色会明显偏灰或偏艳。输出 PNG 要保留原图的 ICC，或在元数据继承时一并带上。

**保存后的可见性（实施定案：走 ①）**：文件移入照片目录后，**当前网格不会自动出现它**——本应用的图片列表来自扫描结果。**已选定 ①「保存成功后主动刷新当前目录」**：实现上复用已测的根 `rescan()`，而不是把新文件本地塞进列表——目录节点的 `directCount / totalCount` 由扫描算出，只改图片数组会让文件夹徽标与磁盘悄悄对不上。同时给一条「已保存为 X，正在刷新列表」的反馈。**不允许什么都不做**——用户点了保存却找不到文件，第一反应是保存失败了。若某次根重扫在超大库上明显慢，再补"按目录增量刷新"，不预先优化。

**同名冲突**：`原名.cutout.png` 已存在时不覆盖，改用 `原名.cutout.2.png`，并在界面上说明为什么多了一个序号——用户必须能预期文件名怎么来的。

### 4.5 对比视图

抠完不是弹个"成功"就结束，而是进入对比视图。**默认模式是按住对比**：按住按钮显示原图、松开显示新图，两张图在同一位置同一尺寸精确叠加。

**为什么按住对比当默认**：它对齐精确、能直接看边缘质量，且不需要用户来回挪视线。左右分屏（原图左、新图右）作为可切换的第二模式保留。

**必须有底纹，否则这条功能是废的**。抠图结果背景透明，若直接铺在窗口上，透明区会被渲染成白底或黑底，用户根本分不清"抠干净了"和"渲染错了"。**底纹定为棋盘格**（用户 2026-09-23 选定），按住时原图铺满棋盘格、松开时结果叠在同一棋盘格上。

> 这条来自探针的实际教训：第一次看生成的 PNG 是白底，完全判断不了透明通道对不对，改成压品红底才看清。不能让用户踩同一个坑。

**左右分屏对抠图天生不利，所以只当次要模式**：U²-Netp 的掩码是在 **320×320** 上算出来的，要放大回原图尺寸再贴 alpha。并排看时右边那张会明显比左边糊，用户会以为是程序坏了。因此：

- 分屏模式下必须在图上注明「掩码在 320×320 下计算」；
- 默认不选分屏，避免用户第一眼就得出"效果变差了"的错误结论。

**v0.8 实现口径**：对比发生在**大图区**——结果**原位替换**那张图的 `src`，"同一位置同一尺寸"由构造保证（同一个元素换图源，不是叠两层再对位）；底栏只放动作（模式切换 / 按住看原图 / 保存 / 不保存）。棋盘格画在 `img` 自身的 CSS 背景上：`object-contain` 的 img 元素盒子等于绘制区，于是**只有透明像素透出底纹**，也不会把底纹铺到照片以外。结果只在它所属的那张照片上有效，翻页即整个消失——挂着一张图的对比到另一张图上是缺陷。

### 4.6 预览后落盘（暂存 → 预览 → 保存才进目录）

处理结果**不直接写进照片目录**，而是先进暂存，用户在暂存上看完再决定：

```
推理完成 → 写入暂存（userData 下，不在任何扫描根内）
              ↓
          预览对比（§4.5）
              ├─ 保存 → 移入原图旁，成为 `原名.cutout.png`，写入继承的标签 + 行为标签
              └─ 不保存 → 什么都不做，文件留在暂存，由清理策略回收（§5.3）
```

**为什么这样更好**：文件从来没进过用户目录，所以"用户相册里冒出半成品"这类问题不存在，也不需要任何"启动时提示处置上次结果"的补丁。

**暂存位置是硬约束**：必须在 `userData` 下。现有扫描器只按扩展名过滤图片（`shared/imageExt.ts`），它不认识 `temp` 这个目录名——**若把暂存放照片目录，半成品会被当成图片扫进用户网格**，直接毁掉这个设计的初衷。

**缓存命中就跳过推理直接预览**：暂存本身即缓存。键 = `原图指纹 + 模型指纹 + 输入尺寸`，其中原图指纹照抄现有缩略图约定 `sha1(absPath : mtimeMs : size)`。同一张图、同一个模型再次点抠图 → 直接给预览，不重跑。

**「丢弃」这个动作消失了**：不保存就是丢弃，不需要一个显式删除按钮。底栏与对比视图因此各少一个操作。

**替换原图：仍然不提供**。要用户自己去资源管理器操作，本应用不做不可逆动作（AG3）。

### 4.7 设置页

**新建应用级「设置」总入口**（顶栏），不做成 AI 专属弹窗。理由：应用现在只有「关于」和「标签管理」两个弹窗，没有任何全局偏好入口；如果 AI 单独开一个弹窗，以后别的全局设置还得再造一个。

**原则：同一份状态只允许有一处可以改。** 模型的下载 / 卸载 / 删除 / 换默认**全部在行为按钮的下拉里**（§4.1），设置页**不再重复提供这些操作**——两处 UI 管同一状态，迟早会不一致。

所以设置页的 AI 分区只有三样东西：**只读统计**、**后处理参数**、**暂存与缓存配置**。

**① 只读统计**：模型总占用、可用磁盘、整卡显存（口径见 §5.2）。要看要删去下拉。

**② 后处理参数。** 调研已完成，来源是 rembg 的 `remove()` 函数签名（Context7 取其 GitHub autodocs，见附录 B）。**结论：除一个例外，全部参数都是掩码后处理，不动模型。**

| 参数（rembg 原名） | 默认值 | 作用 | 要不要重跑模型 | M1 |
|---|---|---|---|---|
| `alpha_matting` | `False` | 开启边缘精修 | 不用 | 候选 |
| `alpha_matting_foreground_threshold` | `240` | 前景判定阈值（0-255） | **不用** | 候选 |
| `alpha_matting_background_threshold` | `10` | 背景判定阈值（0-255） | **不用** | 候选 |
| `alpha_matting_erode_size` | `10` | 腐蚀尺寸，控制留多少边缘 | **不用** | 候选 |
| `post_process_mask` | `False` | 形态学清理掩码 | **不用** | 候选 |
| `decontaminate` | `False` | 去色边 / 溢色 | **不用** | 候选 |
| `bgcolor` | `None` | 用纯色替换背景（RGBA） | **不用** | 候选 |
| `only_mask` | `False` | 只输出掩码，不输出成品 | **不用** | 候选 |
| `vitmatte` + `vitmatte_model` | `False` | 用**第二个模型**精修边缘 | ⚠️ **要，且要多下一个模型** | **不进 M1** |

三点必须记下来，否则这张表会被当成"参数免费可抄"：

- 这些是 **rembg（Python）的参数名**。我们用的是 onnxruntime-node，**没有任何现成实现**——`alpha_matting` 一族在 rembg 里靠 OpenCV 完成，我们要在 JS 侧自己实现等价算法。"参数能调"≠"参数免费"，每个都要单独实现并单独验证。
- `alpha_matting` 一族的耗时**未实测**（纯 CPU 像素运算）。它决定"改参数后多久看到新预览"，实施前必须量，不许默认它免费。
- `vitmatte` 是唯一引入第二个模型的选项，与"模型先只做这一个"直接冲突，**明确排除出 M1**。

**③ 暂存与缓存配置**：预览暂存保留期（默认建议 30 天，可设）、暂存总量上限（超了按最久未用淘汰）。清理逻辑本身在 §5.3。

**M1 的底线不变**：设置页骨架存在、参数区**可以整块为空**，但**不允许出现调了没反应的假控件**——上面这些参数实现哪个，就先验证它真的影响输出，再摆上去。

## 5. 磁盘与显存管理

### 5.0 目录布局（唯一权威定义）

此前模型目录、暂存目录、缩略图缓存、索引文件散在 §5.1、§5.3 与附录 A 三处描述，从未统一——这里一次定死，其余各节只引用不重述。

```
userData/
├── models/                      AI 模型权重，按 modelId 分子目录
│   ├── index.json               本地已装模型索引
│   └── <modelId>/u2netp.onnx
├── ai-preview/                  预览暂存 = 结果缓存（D18）。受 §5.3 清理策略管辖
│   └── <五元组哈希>.png
├── thumbnails/                  缩略图缓存（既有，不动）
├── exiftool-config/             XMP 配置（既有，不动）
├── roots.json / hiddenFolders.json   （既有，不动）
└── settings.json                新增：AI 参数、暂存保留期与容量上限等偏好
```

**三条红线**：

1. `models/`、`ai-preview/` **都不得放在任何照片扫描根内**。扫描器按扩展名过滤（`shared/imageExt.ts`），一旦放进照片目录，模型权重和半成品会被当成图片扫进用户网格。
2. `ai-preview/` 与 `thumbnails/` 分目录，**不混放**——两者清理策略完全不同（缩略图可无脑重建，预览结果关联着用户尚未决定的东西）。
3. 清理逻辑只允许作用于 `ai-preview/` 内路径，删除前校验路径前缀。

### 5.1 磁盘

- 模型文件存放于应用数据目录下的独立子目录，与原图目录完全分离，不与缩略图缓存混放。
- 设置页 AI 分区顶部常驻一行「模型占用 X GB · 可用磁盘 Y GB」。C 盘当前剩 247 GB（实测），但用户可能在别的盘，需运行时读取。
- 下载前预估：`(模型体积) > (可用磁盘 - 安全余量)` 时直接拒绝并说明，不允许下到一半写满磁盘。**安全余量仍未实测**——M0 没有覆盖磁盘写入这一项。实施时按「模型体积 + 一份派生图峰值」来取，定下来之前界面上不显示"预计还需 X"这类推断。
- 删除模型必须同时清掉临时文件与索引记录，不留孤儿。

### 5.2 显存与并发

- 同一时刻**只允许一个推理任务在跑**，其余排队。首版不做并发调度。
- 设置页 AI 分区显示「已用显存 / 总量」（本机实测总量 8151 MiB）。**口径必须标注清楚**：探针能拿到的是整卡 `memory.used`（一次 u2netp 推理 Δ325 MiB，但含机器上其他 GPU 进程），拿不到分进程显存（`nvidia-smi --query-compute-apps` 在本机驱动返回 `[N/A]`）。所以界面应显示"整卡已用"而不是谎称"AI 占用了多少"。
- 加载新模型导致显存不足时：明确报"显存不足，请先卸载 XX"并给一键卸载，**不静默换 CPU 跑**。实测代价差距是 CPU 201ms 对 DirectML 21ms（u2netp，约 10 倍；模型越大差距越大），无声降级会让用户以为程序卡住。若提供"改用 CPU"选项，必须是用户显式勾选，且按 D12 限线程。
- 空闲卸载：**已实施**（2026-09-30）。规则 = 距离最后一次 AI 活动满 **5 分钟** 即释放驻留会话。计时在 `AiService` 里，提交任务与任务结束各重新武装一次，所以量的是"多久没动过"而不是"启动多久"；到点若还有任务在跑或排队，**不抽走在用的会话**，改为延后重计；本来就没有驻留时不去敲空会话。依据仍是加载代价小（0.96s ~ 3.14s）且**加载对用户不可见**（D14：点行为时静默加载），所以激进卸载的代价只是让某次点击多等约一秒，不会多出任何操作步骤。
- 空闲卸载的界面配套：主进程这次释放**不推给渲染层**（不新增事件通道），因此**打开模型下拉必须重取一次清单**——否则空闲之后那行仍挂着绿色的"已加载"，正是 §4.1 第 3 条约束要防的那类谎报。

### 5.3 预览暂存与清理（D18）

- **位置**：见 §5.0 的 `userData/ai-preview/`。**不得放在任何照片扫描根内**——扫描器按扩展名识别图片，放错位置半成品会直接出现在用户网格里。
- **缓存键 = 五元组**（与 D18 ③ 一致，此处为唯一展开说明）：
  `sha1( 原图指纹 : 模型指纹 : 输入尺寸 : 后处理参数 : 预处理管线版本 )`
  - 原图指纹沿用缩略图已有约定 `sha1(absPath : mtimeMs : size)`，不另造一套
  - **后处理参数必须入键**：缓存的是成品图，成品是"模型+参数"的函数。键里不含参数，改阈值后拿到的还是旧图却被当成新结果展示——静默出错，无任何报错。**不存在"当前 M1 无参数所以可以先不入键"这种豁免**：一旦参数实装而键没跟上，就是这个 bug。
  - **预处理管线版本**是手工递增的常量，覆盖解码/EXIF 转正/转码/resize 的实现变更。漏掉它最隐蔽：换了转码器，缓存里全是旧管线烘出来的图，还都对得上键。
- **体积量级**：实测一张 690×920 的成品 cutout PNG = **1119 KB**。按此估算，1000 张约 1.1 GB——所以**必须有总量上限**，只按天数清理不够。
- **清理策略**：保留期（默认建议 30 天，设置页可改）**与**总量上限双条件，任一触发即按最久未访问淘汰。
- **清理只删缓存，不删成果**：用户点过「保存」的文件早已移出暂存，清理逻辑碰不到它。这条要在实现上保证——清理只允许作用于暂存目录内的路径，且删除前校验路径前缀。

## 6. 失败与边界

| 场景 | 表现 | 为什么这样 |
|------|------|-----------|
| 下载中断 | 保留 `.part` 断点，重开可续传 | 实测 hf-mirror 持续下载 **1.27 MB/s**（213.6MB 用 168.8s），一个百 MB 级模型要两三分钟，重头下不可接受 |
| 校验失败（sha256 不符） | 删除文件、报"下载内容损坏，请重试" | 静默用坏文件会在推理阶段崩得莫名其妙 |
| 子进程崩溃 | 主进程感知并重启子进程，当前任务标失败并提示重试 | 用户不能因为一张坏图丢窗口（D9 的全部理由） |
| 显存不足 | 见 5.2 | |
| **保存失败**（目标文件被占用 / 目录只读 / 路径过长 / 磁盘满） | 明确报原因并**保留暂存结果可重试**，绝不静默丢失 | Windows 上"文件被其他程序占用"是日常事件。用户已经看过并认可的结果，不能因为一次写入失败就消失 |
| **EXIF 方向图** | 按 §4.4 规则解码时统一转正，模型输入与输出同方向 | 处理不好会抠出旋转 90° 的图，而 M0 的测试图恰好没有方向标记，**未被覆盖** |
| **宽色域（ICC）图** | 输出保留原图 ICC 剖面 | 丢 ICC 会让 Display P3 之类的照片明显偏色，用户会归咎于"AI 把颜色弄坏了" |
| 原图过大（超模型输入上限） | 处理前按模型规格自动降采样，并在界面注明"已在 NxN 下处理" | 不降采样会直接崩；不注明则用户以为是模型效果差 |
| RAW / HEIC 输入 | 先转码为模型可吃的格式再处理，转码中间文件用完即删；**转码实现变更要同步递增"预处理管线版本"**（§5.3） | 现有代码已记录 RAW/HEIC 写 XMP 可能不被 exiftool 支持，输入侧同样要防 |
| GIF / 多帧图 | 明确拒绝，只处理首帧或提示不支持 | 抠图多帧 GIF 的产物形态没有共识，别猜 |
| 磁盘写满 | 中止、删除已写的**暂存**文件、报剩余空间 | D18 之后写盘目标只有暂存目录，用户照片目录不会被写坏 |
| 无可用 GPU 加速设备 | 清单里所有条目转「不可用」并说明原因，允许显式选择 CPU 慢速模式 | 不能让用户面对一片没有任何解释的灰按钮 |

## 8. M1 验收

以下每条都要在真实构建产物上手动走一遍，不看单测绿灯当交付（M0 探针与 typecheck/test 是证据的一部分，不覆盖行为正确性）：

1. 全新环境（`userData` 下模型目录为空）打开预览 → 底栏出现组合按钮**「抠图 ▾」**，可点击，非灰态，无"请先下载"字样。
2. 首次点主按钮 → 弹一句「首次使用需下载 4.4MB，约 10 秒」→ 确认后**下载→加载→抠图一次走完**，中途不要求第二次点击 → 进入对比视图。
3. 下载中途取消 → 保留 `.part`；再次点击 → 从断点继续，不从头下。下载完成 → 磁盘文件 sha256 与清单一致。
4. 抠图执行 → **此刻照片目录里不应出现任何新文件**，结果只存在于暂存；点「保存」后才有 `原名.cutout.png` 出现在原图旁，且**原图字节未变**（比对 mtime 与 sha256）。推理耗时与 M0 实测的 21ms 同量级（含跨进程传递与图像编解码，允许是它的若干倍，但不应到秒级）。
5. **加载不可见验收**：模型已下载但未加载时点主按钮，用户不应看到任何"加载"字样或额外点击——静默完成（实测 0.96s）。
6. **进行中不置灰**：下载/加载/推理期间按钮以**背景填充**表达进度、文字仍可读、有「取消」。截图对比确认按钮没有变成灰态（D17）。
7. **下拉可纯键盘操作**：不用鼠标，Tab 进入模型菜单 → 方向键选行 → 回车执行「下载」，全程可达；菜单不是 hover 才出现的浮层（D17）。
8. **模型管理只有一个入口**：下拉里能下载/卸载/删除/设为默认；打开设置页确认**找不到**这些重复操作，只有只读统计与参数（D17）。
9. **对比默认是按住模式**：按住显示原图、松开显示结果，两图同位同尺寸精确叠加；**透明区必须落在棋盘格底纹上**（D15 已定为棋盘格），不允许出现纯白/纯黑底导致看不出透明度。
10. 切到左右分屏 → 图上出现「掩码在 320×320 下计算」的注明；不注明则用户会把右图变糊误判成 bug。
11. **能力边界**：用一张人像照与一张非人像照（如风景/演出）各跑一次。前者应抠对；后者**允许选错主体，但不得崩溃、不得报未知错误**，且界面文案不得承诺"去除任意背景"。
12. 派生文件带原图全部标签 + `AI人像抠图` 标签；重新扫描后它能被该标签筛出。
13. **不保存就退出** → 照片目录里始终没有任何新文件；结果只在暂存目录里可查到（D18：没有"丢弃"按钮，不保存即丢弃）。
14. **设置总入口存在**（顶栏可进），AI 分区显示只读统计与参数区；**参数区允许为空，但不允许有假控件**——任何出现的滑块/开关，调了必须真的影响输出。M1 若未定参数项，就整块留空并标注"暂无可调参数"。
15. 底栏**只出现「抠图」一个组合按钮**，没有任何"点了提示不可用"的死条目——未实测的行为与模型一律不进 UI，而不是灰着显示。
16. 强制 CPU 模式 → 界面明确说明当前走 CPU 及其代价；**任务管理器可见 CPU 占用被限制在设定的核数内，不允许占满全部核心**（D12 的直接验收，探针阶段就是漏了这条把机器压死的）。**入口 = 组合按钮下拉底部的「CPU 慢速模式」勾选**；取消勾选后常驻提示必须消失、下一次点击真的走 GPU；勾选状态下**后端变化要重建会话**（连抠两张不同图，第二张不得复用 GPU 会话），这也算本条的验收范围。
17. 构造显存不足（连续加载多个模型）→ 得到可读的"请先卸载 XX"提示，界面不卡死，窗口不崩。
18. **崩溃恢复（用仅开发构建可用的调试入口验证，不是用户功能）**：注入一个已知在 DirectML 上不兼容的模型（如 BiRefNet）→ 推理失败要被捕获成可读提示，且推理子进程崩溃后主窗口存活、子进程被自动重启（D9 的直接验收）。
19. **暂存不污染视图**：暂存目录位于 `userData` 下、不在任何扫描根内 → 重新扫描后用户网格**看不到**任何半成品（这是把暂存放进照片目录会出的事故，D18 ①）。
20. **缓存命中**：同一张图、同一模型、同一参数再点一次「抠图」→ 秒出预览，不重跑推理（日志里应看不到新的 inference 记录）。改动原图（mtime/size 变化）后再点 → 必须重跑，不得复用旧结果。
21. **缓存键必须含参数**（A1 的直接验收）：若参数已实装，改一个参数再点 → **必须重跑并给出不同结果**，绝不允许返回上一次参数的旧图。参数未实装时本项跳过，但 §5.3 的键结构必须已经留好该字段。
22. **预处理管线版本变更使缓存失效**（A4）：手工递增管线版本常量后再点 → 必须重跑，不得复用旧管线烘出的图。
23. **清理的安全边界**：触发保留期或容量上限清理后，已点过「保存」的成果文件必须仍在原处。实现上清理只允许作用于暂存目录内路径，且删除前校验路径前缀（§5.0 红线 3、§5.3）。
24. **EXIF 方向图**（A3）：用一张带 Orientation 标记（像素横向、需旋转显示）的照片跑一次 → 结果方向与原图**视觉一致**，不得抠出旋转 90° 的图。M0 探针的测试图没有该标记，所以这条此前**完全未被覆盖**。
25. **保存失败不丢结果**（A5）：把目标文件设为被其他程序占用或目录只读，再点保存 → 报出可读原因，**且暂存结果仍在、可直接重试**，不需要重新抠一遍。
26. **保存后可见性**（C2）：点保存成功后，新文件要么立刻出现在当前网格，要么界面明确提示"已保存，需重新扫描后显示"。**不允许静默**——用户找不到文件就会认为保存失败。
27. **AG1 的可验证证据**（C3）：完成一次抠图（模型已下载）后，用系统连接表或抓包确认处理期间**没有任何出站网络请求**。AG1 是声明，这条才是证据。
28. 对 RAW、GIF、超大分辨率图各跑一次 → 均落入 §6 表格中某一行的预期表现，无未捕获异常。

### 9.1 Q11 的裁定：标签词表策略（2026-10-07 用户定）

> **用户原话**：「标签可以自动生成，**但已有已经加上去的不要动**」。

这条裁定**偏离了文档此前的推荐方向**，记录理由与边界：

- 文档原先倾向「用现有标签库当词表」，顾虑是内置通用词表会**产生用户没见过的标签**，与 PRD US7「统一标签命名、避免同义标签混乱」冲突。
- 用户的裁定是**只增不改**：自动生成新标签可以，**已打在图片上的标签一个字都不许改**。
- 这条路可行的关键在于**「污染」被限定为「新增」而非「篡改」**：用户已有的标签体系不会被自动打标改写，同义标签风险仅存在于「新增的那一批之间」，且用户随时可删。

#### 落成规则

| # | 规则 | 说明 |
|---|------|------|
| 1 | **已存在的标签只读不改** | 自动打标**不得**重命名、合并、删除任何已有标签。`TagManagerDialog` 的重命名/合并是用户手动动作，模型不参与 |
| 2 | 新标签由模型生成 | 候选词表**不由代码内置**，而由模型从图像内容直接产出（SigLIP 零样本可对任意标签文字打分，不受词表限制） |
| 3 | **必须给置信度** | 每个自动标签带一个相似度分数，**低置信度的宁可不打**。阈值未定，属实现期决策 |
| 4 | 落成位置可换 | 已定（D3）：写入图片自身 `XMP-ptm:Tags`，与手打标签同处一个字段。⚠️ 这意味着**用户无法一眼分出哪些是机器打的**——实现时需考虑是否加标记（如来源前缀）或其他可辨识手段，**此项未定** |
| 5 | 零样本的能力边界要写进界面 | SigLIP 认的是 WebLI 语料里的通用概念，**认不出「爷爷的生日」这类私人语义**。文案不得暗示「什么都能自动认」 |

#### ⚠️ 规则 2 有一个技术前提尚未验证（**这条最容易被误解**）

「自动生成标签」在**技术上有两种截然不同的做法**，成本差一个量级：

| 做法 | 怎么工作 | 需要什么 | 能生成什么 |
|---|---|---|---|
| **A. 开放式打标** | 模型直接从图像特征「说出」标签名 | **做不到** —— 零样本模型必须先拿到**文字**才能算相似度 | 无 |
| **B. 候选式打标** | 准备好一批候选标签文字，让模型逐个打分，取过阈值的 | **需要一份候选词表** | 只能从候选里挑 |

**SigLIP 属于 B 类，绕不开候选词表。**它不是「看图说话」的模型（那是 A15BLIP-2 / Florence-2 那类，500 MB 起且撞 K3），它是「给一张图和一个词，打个分」的评分器。

所以规则 2 的准确表述应该是：**候选标签由内置通用词表提供，模型负责从中挑出合适的** —— 也就是文档原先推荐的 B2 方案，而不是「模型凭空造词」。用户裁定的是**只增不改**（不对已有标签下手），这部分完全成立且已落地成规则 1。

**这意味着候选词表从哪来这个问题（Q11 的原问题）依然存在**，只是它现在不再是「用用户的标签 vs 内置词表」的二选一，而是：

| 子问题 | 状态 |
|---|---|
| 候选词表**来源**（内置通用词表 / 两者合并） | **待定**。建议内置为主 + 掺入用户已有标签，这样既有覆盖面又不浪费已有体系 |
| 词表**规模与语言**（多少个词？中文还是英文？） | **待定**。SigLIP 的中文能力**未实测**（卷宗 §5 未验项3），这决定词表能不能用中文 |
| 置信度阈值 | **待定**，且**依赖候选词表先定** |

#### 这条裁定尚未解决的事（**不许当成已完成**）

| # | 项 | 状态 |
|---|----|------|
| 1 | **真图准确率 + 相似度分布** | ✅ **已实测 2026-10-07**（13 张用户真实照片）。top1 命中 8/13、进前三 10/13。**但词表只 16 个词，不能外推到真实词表规模** |
| 2 | **候选词表定稿** | ⛔ **实测已排除中文**：官方 tokenizer 词表里中文单字 0 个，中文得分 0/13 张胜出。**必须英文词表 + 界面中文映射**。词表规模/门类仍待定 |
| 3 | **置信度判据** | ⚠️ **绝对值阈值这条路已排除**。实测相似度区间 `-0.0821 ~ 0.0692`、大量为负（sigmoid loss 所致），照搬 CLIP 的「>0.25 即匹配」会全军覆没。**须改用相对判据**（如 top1-top2 差值），具体形态待实测标定 |
| 4 | **换官方 tokenizer** | 本轮用自写贪心最长匹配，生产须换 `@xenova/transformers` 或官方实现 |

**所以：模型级准入已过（`../models/siglip.md`），功能级准入未过** —— 本节只锁定了词表策略这一项产品决策，其余四条见卷宗 §7 待办。

### A.2 新增 IPC 通道（沿用 `域:动作` + `IpcResult` 信封约定）

ai:run-batch          → 多张，M4 才注册
