# GPU 底座自检设计（Self-Probe）

> **历史设计文档（2026-10-20）**：PhotoTagManager 当前版本已移除人像抠图、AI 处理 UI、模型下载和 ONNX 推理链路。本文仅记录早期设计与实现决策，不是当前产品规格或能力承诺；文中引用的 `electron/ai/**` 代码路径已随该链路一并删除。
> 建档 2026-09-29。触发点：用户问"我电脑是 5060，别人不一定，怎么判断什么显卡能跑什么模型"。
> 本文只设计**底座自检**这一件事；模型准入仍归 `ai-photo-processing.md` §4.3，能力边界仍归 K1–K6（见 `image-model-capability-map.md` §1/§1.5）。

## 1. 要解决的问题

软件装到用户机器上，**我们不知道他那台机器的显卡加速底座通不通**，于是只能等用户点了抠图、转了十几秒、看到一条错误。现有探测只会答"有没有显卡设备"，答不了"能不能真的算"。

## 2. 三条已实测的依据（设计建立在它们之上，不是推测）

| 结论 | 来源 |
|------|------|
| 系统的显存查询字段**谎报一半**：8151 MiB 的卡被报成 4095 MiB | 2026-09-29 本机实测（取证命令见 `image-model-capability-map.md` §10） |
| Electron `app.getGPUInfo` **读不到显存**，且 `supportsDx12=false` 与"DirectML 实测可用"**互相矛盾**，不能当 AI 能力判据 | 2026-09-29 探针实测（`getGPUInfo` 每卡字段只有 active/vendorId/deviceId/driverVersion/gpuPreference 等） |
| 底座自检**跑得动且很便宜**：DirectML 加载 1470 ms、推理 27.1 ms、整卡显存 +337 MiB；纯 CPU 推理 243.4 ms | 2026-09-29 用仓库夹具 `tests/fixtures/models/u2netp.onnx`（4.36 MB）实测三组 |

**这三条合起来指向同一个结论：静态查询这条路基本出局，判定只能靠"真跑一次"。**

顺带从第三行挖到一个可用的判据：走显卡时显存 **+337 MiB**，走纯 CPU 时 **+0 MiB**。这个差值让"名义上成功但悄悄回落到 CPU"变得**可检测**（现在代码里 `executionProviders: ['dml','cpu']` 的回落是无日志、不可见的）。

## 3. 必须守住的既有裁定（本设计一条都不破）

| 既有裁定 | 对本设计的约束 |
|---------|--------------|
| **D12 绝不自动退回 CPU** | 自检发现底座不可用，**只标注**，不自动切换、不自动降级。 |
| **§4.3 只有实测跑通的条目才能进 UI** | 自检是**底座**探测，**不是模型准入**。u2netp 跑通不代表 BiRefNet 能跑（本项目有先例：同一引擎、加载成功、一执行就崩）。 |
| **AG1 零出站** | 探针模型必须**内置**，绝不允许自检触发下载。自检全程不得产生网络请求，这条要纳入 §8-27 的抓包验收。 |
| **AI 设置分区零 `input` 防线**（`tests/ai/aiSettings.test.tsx:140`） | 该断言禁的是滑块/勾选/文本框。**自检按钮是 `<button>`，不在禁止范围内**，且它真会触发动作——符合这条防线的本意（不许假控件），不是钻字面空子。**不得**借机往设置页塞任何参数控件。 |

## 4. 设计

### 4.1 什么时候跑：按硬件指纹，不是每次开机

探针一次约 1.5 秒且要占 GPU。每次开机都跑既浪费，又会让用户在"什么都没干"时看到显存跳动、风扇起转。

改成**跑一次，按指纹失效**：

```
指纹 = vendorId + deviceId + driverVersion + gpuPreference + 引擎版本
        └── 全部来自 app.getGPUInfo('complete')，2026-09-29 已实测这些字段可读
```

- 没有档案 → 跑一次
- 指纹变了（换驱动 / 插拔外置显卡 / 笔记本切独显直连）→ 重跑
- 指纹没变 → 直接用缓存，**什么都不跑**
- 用户在界面点「重新自检」→ 无视缓存重跑

**注意实测到的一个坑**：同一张物理卡会被 `gpuDevice` 重复枚举（本机 6 条记录里 RTX 5060 占 4 条），且 `basic` 模式下所有 `active` 都是 false。所以**必须用 `complete`，且指纹要去重后只取 `active=true` 或 `gpuPreference` 最高那一条**，不能拿数组长度当"有几块卡"。

### 4.2 跑什么：内置极小模型

- **本期用现有夹具那份 u2netp（4.36 MB）已经验证机制成立**，但它要进安装包才不触发下载（当前 `package.json` 无 `extraResources`，模型是按需下载的）。
- **最终形态是把探针模型缩到 KB 级**（合成一个只含一层的 ONNX）。这需要一次性生成工具（Python 有 3.13 但**没有 onnx 库**），属独立小任务，**不是本期阻塞项**。
- 无论多大，探针模型**必须是内置的**，因为 §3 的 AG1 那条。

**输入用固定种子的伪随机张量**，不用全零——全零可能走到退化路径，测出来的耗时不代表真实情况。

### 4.3 在哪跑：必须在推理子进程

DirectML 有把进程打崩的先例（BiRefNet 的 `DmlFusedNode`），所以自检**绝不能跑在主进程**。复用现有 `utilityProcess` 子进程与崩溃恢复链路（D9），并复用其已有的**超时与崩溃捕获**：自检失败必须落成一条可读结果，而不是让程序消失。

同时要跑**两条路各一次**：`['dml','cpu']` 与 `['cpu']`，且 CPU 那次**必须限线程**（`intraOpNumThreads`，M0 就是没限把整机压到无响应）。这是 §2 那个显存差值判据成立的前提——没有 CPU 对照组，就无法区分"回落了"和"本来就这样"。

### 4.4 测什么、存哪里

每次自检产一条记录：

```
指纹 / 日期 /
dml：加载耗时、推理耗时、显存增量 /
cpu：加载耗时、推理耗时（限 2 线程）、内存增量 /
结论：可用 | 不可用 | 未知 + 一句原因
```

**存 `userData` 下独立文件**（如 `gpu-probe.json`），**不进 `settings.json`**。理由：`settings.json` 存的是用户偏好（`scanDoneToast`、`proxyRules`），而这是程序写的测量结果。混在一起会导致"恢复默认设置"误删机器档案，也会让 settings 的字段语义变质。

**显存口径必须注明是整卡**（含其他 GPU 进程），界面只能写"整卡已用"，不能写成"AI 占用多少"——这是 `gpuStats.ts` 已经定过的诚实口径。

### 4.5 结果怎么影响界面

自检结论**只挂原因，不改状态字段**：沿用现有做法（`AiModelStatus` 是磁盘真相，能力判断走 `statusReason`），新增一档"本机加速底座"的说明文案，下拉里那行「· 不可用」的原因改由自检结论提供。

**落点已有先例，不需要新决策**：`src/components/AiActionSplitButton.tsx:309` 那个「· 不可用」只是**文案标记，没有 `disabled`**；同文件 `:140` 的注释还写着"进行中不置灰：用 disabled 表达忙会让人以为程序坏了"。所以本项目的一贯取向就是**标注但始终可点**，自检结论直接沿用同一机制。

四条判定：

| 结论 | 判据 | 界面 |
|------|------|------|
| **可用** | dml 成功 **且显存增量 > 阈值** | 正常显示，标注"已自检于 X 天前" |
| **名义成功但回落** | dml 调用成功 **但显存增量 ≈ 0** | 视为**不可用**并如实说明"检测到计算实际落在 CPU 上"——这正是现在看不到的那种失败 |
| **不可用** | dml 报错 / 超时 | 沿用现有「· 不可用」+ 原因，并提示可勾 CPU 慢速模式 |
| **未知** | 探测本身跑不起来 | **一律按"可用"处理**（现有 `unknown` 的取向，绝不误挡能用的机器） |

**回落阈值不拍数字**：本机实测 dml +337 MiB、cpu +0 MiB，差值很大，候选线取"增量 < 32 MiB 视为回落"，但**必须在多卡/多负载机器上校准后才进产品**。

### 4.6 用户在哪看到、能不能手动重跑

设置页 AI 分区加**一行只读信息 + 一个按钮**：

> 本机 AI 加速：**可用**（GeForce RTX 5060 Laptop GPU，自检于 3 天前）  〔重新自检〕

- 只读那行用 `getGPUInfo` 里的 `glRenderer` 取可读卡名（2026-09-29 实测该字段带卡名），**仅用于显示，不用于判定**。
- 「重新自检」是按钮、不是参数控件，符合 §3 那条防线。
- 不做开关、不做定时、不做静默到无人知情。

## 5. 明确不做（省得被塞回来）

- ❌ **不猜"哪个模型能不能跑"**——只有真模型真图实测能答（§4.3 老规则）。
- ❌ **不自动退回 CPU**（D12）。
- ❌ **不把条目置灰挡死**——探测本身会谎报（§2 第一行），最多标注，仍允许点。
- ❌ **不做每次开机都跑**。
- ❌ **不引入 DXGI / 原生模块去拿精确显存**——除非以后有明确需要，本期用"跑一次"绕过这个缺口。

## 6. 风险与未决

| # | 问题 | 影响 |
|---|------|------|
| P1 | **双显卡机器上 DirectML 到底选哪块卡，从未验证**（本机是 610M 核显 + 5060 独显） | 若默认选到核显，所有耗时数字失去意义。**这是开工前最该先测的一项**，且它可能需要在探针里显式指定适配器 |
| P2 | 探针模型 4.36 MB 进安装包 vs 缩到 KB 级 | 安装包 121 MB → 约 125 MB；缩到 KB 级要一次性生成工具 |
| P3 | 回落判据的阈值未经多机校准 | 见 §4.5 |
| P4 | CPU 侧"大模型越线"的阈值仍**完全没有数据**（26 MB / 101 MB 档从未测过） | K6 的那条线还是待定，本文不解决 |
| P5 | `['dml','cpu']` 的静默回落本身要不要改成 `['dml']` | 属既有隐患，本期只提供"能看见它"的手段，不改行为 |

## 7. 验收怎么写（要能失败，不写绝对阈值）

1. 有档案且指纹未变 → 启动**不产生任何推理调用**（用子进程日志数验证，不是看界面）。
2. 删掉档案 → 启动后空闲期跑一次，档案里出现 dml 与 cpu **两组**数字。
3. 换指纹（改驱动版本字段即可模拟）→ 必须重跑。
4. 自检全程**零出站请求**（并入 §8-27 的抓包验收，动作归因要能区分是自检还是用户操作）。
5. **反证腿**：人为把探针指向一个已知在 DirectML 上会崩的模型 → 自检必须落成"不可用 + 原因"，**进程不能消失**，主窗口必须还活着。
6. **对照组**：`PTM_FAKE_GPU=none` 下自检应给"不可用"，`unknown` 分支应给"按可用处理"，两者不得混淆。
7. 设置页那一行显示卡名与自检日期；**断言 AI 分区仍然零 `input`**（沿用现有防线，不削弱）。

## 8. 开工顺序

```
第 0 步（先做，风险最高）：验 P1——双显卡机器上 DirectML 实际选哪块卡
   ↓ 结论会影响探针要不要显式指定适配器
第 1 步：探针跑在子进程 + 两组对照 + 档案落 userData 独立文件
   ↓
第 2 步：硬件指纹与失效逻辑
   ↓
第 3 步：设置页只读行 + 重新自检按钮（顺带确认没削弱零 input 断言）
   ↓
第 4 步：回落判据阈值在多机校准后才进文案
   ↓
第 5 步（独立小任务）：把探针模型从 4.36 MB 缩到 KB 级
```
